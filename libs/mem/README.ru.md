# libmem — помощник для работы с памятью
`libmem` — это небольшая библиотека на чистом C (C2x), которая прячет управление динамической памятью, чтобы код приложения был сосредоточен на логике, а не на рутинной работе с `malloc`.

Библиотека прозрачно умеет работать с HugeTLB, Transparent Huge Pages и выравниванием выделяемой памяти (TODO)

## Архитектура

### Структура каталога библиотеки

```
.
├── .builds/             # артефакты сборки (создаётся `make`); внутри подкаталоги конфигураций (`debug/`, `production/`, `portable/`), каждый с `libs/` и внутренним `libs/obj/`
├── src/
│   ├── mem_*.c          # реализации отдельных функций
│   ├── mem_telemetry.c  # телеметрия и глобальное состояние
│   └── mem.h            # публичный API
├── tests/
│   ├── src/             # поддерживаемые примеры использования и регрессионные тесты
│   └── Makefile         # сборка тестов
└── Makefile
```

### Сборка

`Makefile` поддерживает несколько конфигураций сборки:

```sh
# Отладочная сборка (O0 + отладочные символы, вывод в .builds/debug)
make debug

# Production-сборка (O3 + LTO, вывод в .builds/production)
make production     # или `make prod`

# Портируемая сборка (generic tune, вывод в .builds/portable)
make portable

# Сборка с AddressSanitizer/UBSan
make sanitize

# Очистка сгенерированных артефактов
make clean

# Быстрое удаление всей директории .builds/ с артефактами
make purge
```

Во всех конфигурациях исходники компилируются из `src/`, объектные файлы складываются в `.builds/<config>/libs/obj/`, а статическая и динамическая библиотеки появляются в `.builds/<config>/libs/`.

### Как подключить библиотеку

`libmem` можно подключить двумя способами: использовать готовую библиотеку из её сборочных артефактов или встроить исходники из `src/` прямо в свой проект

Первый вариант — собрать `libmem` через её `Makefile` и подключить готовый `libmem.a` или `libmem.so`. Из каталога `libs/mem/` выберите нужную конфигурацию:

```sh
make debug
make production
make portable
make sanitize
```

При прямом запуске `libs/mem/Makefile` артефакты создаются в локальном каталоге `libs/mem/.builds/<config>/libs/`: статический архив `libmem.a` и динамическая библиотека `libmem.so`. Объектные файлы остаются внутренними артефактами в `libs/mem/.builds/<config>/libs/obj/` и не должны подключаться приложением напрямую

Приложение подключает публичный заголовок из `libs/mem/src/mem.h` и добавляет include path к этому каталогу, например `-I.../libs/mem/src`. На этапе линковки укажите каталог с артефактами выбранной конфигурации, например `-L.../libs/mem/.builds/production/libs -lmem`. Если используется статический `libmem.a`, нужно также слинковать зависимости библиотеки той же конфигурации, прежде всего `librational`

Когда сборку запускает общий `libs/Makefile` или верхнеуровневая сборка проекта, `BUILDDIR` переопределяется, поэтому артефакты библиотек попадают в проектный `.builds/<config>/libs/` в корне репозитория. Механизм подключения остаётся тем же: заголовок берётся из `libs/mem/src/`, а линковка идёт с артефактом `libmem` из выбранной конфигурации

Второй вариант — скопировать содержимое `libs/mem/src/` в свой проект, подключить заголовочный файл `mem.h` и добавить все `.c` файлы библиотеки в собственную систему сборки. В этом случае проект сам решает, как компилировать исходники и куда складывать объектные файлы или итоговые артефакты. Нужно только, чтобы код приложения и все исходники `libmem` видели `mem.h`, а компилятор использовал совместимый режим C2x. Так как `libmem` зависит от `librational`, эту зависимость тоже нужно добавить в проект: через готовый артефакт `librational` или через её исходники

## О библиотеке

### Что умеет

* Безопасные выделение и очистка памяти в куче (heap)
* Операции со строками произвольной ширины символов. Ширина действительно может быть любой. Например: `char`, `signed char`, `unsigned char`, `char8_t`, `wchar_t`, `char16_t`, `char32_t`
* Безопасное копирование и конкатенация буферов и строк, в том числе self-aliasing
* Расчёт видимой длины строк по привычному принципу поиска нулевого терминатора, как в `strlen(...)`, но с учётом ширины элемента и с кэшем длины для строковых дескрипторов
* Поддержка self-aliasing на любых операциях
* Защита от переполнения буфера и целочисленного переполнения
* Повторное использование дескриптора после освобождения принадлежащего ему буфера через `m_del(...)`. Это своеобразная защита от ситуаций "use after free"
* Повторное использование уже выделенных блоков (см. [«Флаги поведения `m_resize`»](#флаги-поведения-m_resize))
* TODO: прозрачное адресное выравнивание выделяемых буферов. `MEMORY_BLOCK_BYTES` должен использоваться как запасное значение минимального блока, если размер страницы памяти не удалось получить у операционной системы
* TODO: прозрачное выделение через Huge Pages с адресным выравниванием. Отдельные флаги сборки или настройки должны выбирать обычный heap, выровненный heap, явные Huge Pages или Transparent Huge Pages

Публичным API для прикладного кода считаются входные точки с именами `m_*`. Имена `mem_*`, которые остаются в `mem.h`, относятся к низкоуровневому внутреннему слою и предназначены для самой библиотеки или для узких продвинутых сценариев.

### Каркас и поток

Это фундаментальный принцип библиотеки: разделение того, что создаёт программист (каркас), и того, с чем программа работает в рантайме (поток данных).

#### Каркас

Каркас — это то, что создаёт программист. Программист может случайно неправильно использовать библиотеку, и библиотека гарантирует, что даст об этом знать сообщениями об ошибках.

#### Пример 01. Ошибка каркаса при строковой операции над data-дескриптором

Проверяется тестом [`test_libmem_0000_01`](tests/src/test_libmem_0000.c#L32)

Пример сообщения об ошибке при попытке применить функцию для работы со строками к дескриптору, предназначенному для хранения сырых бинарных данных:

1. Создаём дескриптор со значениями по умолчанию:

```c
m_create(char,destinations_string);
```
Это создаст дескриптор для работы с сырыми данными, а не для хранения строк.

2. Пытаемся скопировать строку в память, описанную дескриптором:

```c
// Исходная строка в стеке
const char *source_string = "Hello world";

// Попытка копирования из исходной строки в целевой дескриптор
m_copy_string(destinations_string,source_string);

// Очистка памяти после использования
m_del(destinations_string);
```

3. Ошибка проектирования. При попытке использования `m_copy_string()` получим сообщение об ошибке. Дескриптор не был объявлен с флагом `MEMORY_STRING` как дескриптор для хранения строк, поэтому попытка хранить в нём строку приведёт к сообщению об ошибке на этапе разработки программы:

```
ERROR: src/mem_core_string.c:mem_core_string:123 Memory management; Destination must be a string descriptor
```

4. Описание причины. Библиотечные функции ведут себя по-разному с дескрипторами для хранения строк и с дескрипторами для хранения данных. Это связано с их природой: строки нуль-терминированы, и это должно отдельно учитываться, например, при конкатенации или изменении размера. Сырые данные не предполагают ни обрезки, ни отсечения нуль-терминаторов, что тоже требует отдельных алгоритмов контроля. Поэтому в библиотеке предусмотрены разные пути работы с разными видами дескрипторов. По умолчанию (как в указанном примере) дескриптор создаётся как дескриптор для хранения бинарных данных.

5. Есть два пути решения.

#### Пример 02. Дескриптор сразу создаётся в строковом режиме

Проверяется тестом [`test_libmem_0000_02`](tests/src/test_libmem_0000.c#L54)

В момент создания можно объявить дескриптор как готовый для работы со строками:

```c
// Тут не будет ошибок — дескриптор создан с флагом, объявляющим его для хранения строк
// с символами произвольной ширины. В данном примере это однобайтовый знаковый тип char.
m_create(char,destinations_string,MEMORY_STRING);
const char *source_string = "Hello world";
m_copy_string(destinations_string,source_string);
m_del(destinations_string);
```

#### Пример 03. Data-дескриптор преобразуется в строковый режим

Проверяется тестом [`test_libmem_0000_03`](tests/src/test_libmem_0000.c#L78)

Второй путь — преобразовать дескриптор для хранения данных в дескриптор для строк:

```c
// Тут тоже не будет ошибок. Сначала дескриптор создан с флагом по умолчанию MEMORY_DATA,
// объявившим его для хранения сырых байт, но потом дескриптор преобразован в тип
// для хранения строк, и проверки на вид дескриптора будут успешно пройдены при вызове m_copy_string().
m_create(char,destinations_string);
m_to_string(destinations_string);
const char *source_string = "Hello world";
m_copy_string(destinations_string,source_string);
m_del(destinations_string);
```

#### Поток

Поток — это те данные, которые созданная программа размещает в куче, обрабатывает и вычищает по требованию. В этом случае данные неприкосновенны и предполагается, что они могут быть какими угодно, и это ни при каких обстоятельствах не может привести к ошибкам библиотеки, краху программы или сообщениям об ошибках во время штатной работы. Другими словами:

* Библиотека гарантирует сообщения об ошибках на этапе проектирования программы
* Библиотека гарантирует отсутствие любых ошибок потока данных в случае, когда код программы стабилен
* Библиотека гарантирует неприкосновенность данных. Они не будут испорчены библиотекой и не приведут к падению или остановке программы

### Архитектурные принципы

- **Безопасный self-aliasing как обязательное правило:** операции библиотеки должны корректно обрабатывать случаи, когда источник указывает внутрь `destination`. Если конкретная функция этому ещё не соответствует, это считается дефектом или техническим долгом, а не альтернативной нормой API
- **Отслеживание типа:** под «типом» здесь имеется в виду тип одного элемента, который будет храниться в дескрипторе — например, `char` для байтовых строк, `wchar_t` или `char32_t` для широких строк, либо любой пользовательский тип, например структура `struct point`. При создании через `m_create(T, name)` библиотека запоминает размер этого типа в `sizeof(T)` байт, и потом при каждом доступе через `m_data(T, name)` или `m_data_ro(T, name)` проверяет, что запрошенный тип совпадает с зафиксированным. Если попытаться прочитать дескриптор как «другой» тип, доступ вернёт `NULL` вместо того, чтобы молча отдать память с неправильной интерпретацией:

  ```c
  m_create(int,values);             /* sizeof(int) сохранён внутри дескриптора */
  if((TRIUMPH & m_resize(values,8)) == 0)
  {
  	return(FAILURE);
  }

  int *as_int = m_data(int,values);    /* типы совпадают — получаем рабочий указатель */
  char *as_char = m_data(char,values); /* размеры элементов разные — вернётся NULL и сообщение об ошибке */
  ```
- **Явная инициализация:** дескриптор `memory` хранит несколько связанных полей (размер элемента, длину, флаг режима, указатель на буфер). Если объявить переменную `memory` без инициализации, в полях окажется мусор, и любая публичная функция отвергнет такой дескриптор как испорченный. Чтобы этого не было, используется одно из двух семейств макросов:

  - **`m_init(T)` / `m_init(T, MEMORY_DATA)` / `m_init(char, MEMORY_STRING)`** — для случаев, когда инициализация делается во время выполнения: присваивание существующей переменной, передача результата в функцию, локальный compound-literal внутри блока кода. Макрос разворачивается в вызов, который возвращает готовое значение `memory` с корректным `->single_element_size`, нулевыми длинами и выбранным режимом без выделения памяти.

    ```c
    memory buffer = m_init(char, MEMORY_STRING); /* пустой строковый дескриптор для char */
    /* далее можно вызывать m_resize(&buffer, ...), m_copy_string(&buffer, ...) и т.д. */
    ```

  - **`m_init_static(T, ...)`** — для случаев, где компилятор требует **константного** инициализатора: глобальные и статические переменные, поля структур на уровне declaration, элементы статических массивов. Макрос разворачивается в designated-initializer-список, который годится в таких контекстах.

    ```c
    static memory global_log = m_init_static(char, MEMORY_STRING); /* живёт всё время работы программы */
    ```

  Для обычных локальных переменных проще всего использовать `m_create(T, name)` — он создаёт корректный дескриптор, задаёт размер одного элемента, обнуляет длины, указатель и служебные поля. Если после этого дескриптор выделял память в куче, её всё равно нужно явно освободить через `m_del(...)`. `m_init` / `m_init_static` нужны именно тогда, когда `m_create` не подходит структурно (например, член структуры или глобальный объект)
- **Безопасное изменение размера:** при `m_resize` библиотека сама пересчитывает нужный объём памяти и проверяет, что вычисления не переполнятся, поэтому даже очень большие размеры не приведут к скрытой ошибке. Внутри библиотека старается переиспользовать уже выделенный блок, чтобы рост или уменьшение буфера не превращались в каждый раз новое обращение к системе — это делает повторные изменения размера дешевле и предсказуемее. Подробности и флаги поведения см. в [«Флаги поведения `m_resize`»](#флаги-поведения-m_resize)
- **Два уровня прямого доступа к памяти:** `m_data(...)` и `m_data_ro(...)` дают указатель на содержимое дескриптора и попутно убеждаются, что дескриптор в адекватном состоянии и тип элемента совпадает с тем, что было задано при создании. Если что-то не так — возвращается `NULL` и выводится сообщение об ошибке вместо аварийного завершения. `m_raw_data(...)` и `m_raw_data_ro(...)` выполняют только минимальные проверки состояния дескриптора и не проверяют тип элемента — это нужно там, где код вызывается часто, а состояние дескриптора уже известно и не вызывает сомнений. При успешном вызове raw-функции возвращают живой указатель на тот же буфер `descriptor->data`, а не копию; записываемый и read-only raw-виды одного дескриптора указывают на одну и ту же память.

Все четыре функции сами по себе не меняют режим дескриптора (строка/данные) и не трогают кеш длины строки — они только дают доступ к памяти

### TODO: Аллокация и реаллокация памяти

Этот раздел описывает схему низкоуровневого управления памятью в `libmem`. Прикладной код не выбирает напрямую между `malloc`, `mmap`, Huge Pages или выровненными блоками: этим занимается библиотека. Для пользователя основной точкой входа остаётся `m_resize(...)`, а детали выбора стратегии спрятаны внутри.

Логический размер, описанный в дескрипторе `memory` и физически зарезервированная память — это разные вещи. Поле `length` хранит количество логических элементов размера `single_element_size`, которые видит вызывающий код. Поле `actually_allocated_bytes` хранит, сколько байт библиотека реально зарезервировала на нижнем уровне памяти. Это значение может быть больше, чем `length * single_element_size`, потому что библиотека может округлять запрос до размера страницы, Huge Page или другого выбранного блока резерва.

Размер обычной страницы памяти определяется непосредственно при аллокации или реаллокации физического хранилища дескриптора через `sysconf(_SC_PAGESIZE)` или `sysconf(_SC_PAGE_SIZE)`. Это платформозависимое значение: на многих x86-64 Linux-системах обычная страница равна 4 KiB, на ARM/AArch64 часто встречаются 4 KiB, 16 KiB и 64 KiB, macOS на Intel обычно использует 4 KiB, а macOS на Apple Silicon часто использует 16 KiB. Эти числа приведены только как примеры. Код не полагается на них напрямую. Если размер страницы получить не удалось, запасным значением используется `MEMORY_BLOCK_BYTES`.

Расчёт итогового размера физического резерва выполняет внутренняя функция `mem_resize_calculate_allocation_bytes(...)`. Она принимает логический запрос в элементах, размер одного элемента и конфигурацию backend-а памяти, заданную флагами сборки, проверяет переполнение арифметики и возвращает размер резерва в байтах. Именно этот рассчитанный размер затем сохраняется в `actually_allocated_bytes` после успешного изменения физического хранилища.

Выделением и изменением размера физического хранилища занимается внутренняя функция `mem_resize_storage(...)`. Ей передаётся сам дескриптор `memory`: функция читает из него текущие `data` и `actually_allocated_bytes`, выполняет аллокацию или реаллокацию, а после успешного изменения записывает обратно новые `data`, `actually_allocated_bytes` и фактический `storage_backend_type`. Поле `storage_backend_type` отражает вид хранилища, который реально удалось получить, а не только backend, запрошенный флагами сборки. Для обычной heap-памяти backend использует `malloc`, `calloc` и `realloc`. Поэтому пользователь может применять drop-in аллокаторы вроде mimalloc, jemalloc, TCMalloc и других, если они подключены к приложению.

Полное освобождение буфера, который принадлежит дескриптору, выполняет `m_del(...)`. Прикладной код не освобождает `memory->data` напрямую и не выбирает между `free(...)` и `munmap(...)`. Дескриптор хранит фактический тип уже выделенного физического хранилища, а `m_del(...)` автоматически выбирает правильный механизм очистки для этого типа: для heap-backed памяти он опосредованно использует `free(...)`, а для mmap-backed памяти — `munmap(...)`.

Если задан флаг сборки `#define MEMORY_USE_ALIGNED_STORAGE`, `mem_resize_storage(...)` выделяет блоки с адресным выравниванием. Для такого backend-а используются `posix_memalign(...)` или `aligned_alloc(...)`: если флагами сборки определён POSIX-совместимый код, выбирается POSIX-совместимая функция, иначе используется `aligned_alloc(...)`. Полное освобождение всё равно выполняется через `m_del(...)`. Переносимого API для реаллокации выровненного блока с сохранением заданного выравнивания нет ни в C11, ни в POSIX, поэтому изменение размера такого блока обычно означает выделение нового блока, перенос данных и освобождение старого. Это может дать выигрыш для некоторых рабочих нагрузок, но при частых изменениях размера может ухудшить производительность: библиотеке приходится чаще выделять новый блок, копировать старые данные и освобождать прежний блок.

Если задан флаг сборки `#define MEMORY_USE_HUGE_PAGES`, библиотека пытается выделять крупные страницы памяти через Huge Pages. На Linux явные HugeTLB-страницы обычно запрашиваются через `mmap(..., MAP_HUGETLB, ...)`. Отдельная политика `#define MEMORY_USE_TRANSPARENT_HUGE_PAGES` использует обычное отображение памяти и подсказку ядру через `madvise(..., MADV_HUGEPAGE)`. Transparent Huge Pages не гарантируют, что память действительно размещается на Huge Pages: ядро принимает окончательное решение само.

Huge Pages зависят от процессора, операционной системы, настроек ядра и доступного заранее зарезервированного пула. Часто встречается размер 2 MiB, на x86-64 при поддержке процессора и ядра могут быть доступны 1 GiB страницы, а на ARM64/AArch64 набор размеров зависит от базового размера страницы и конфигурации ядра. Минимальный желаемый размер Huge Page задаётся через `#define MEMORY_HUGE_PAGE_BYTES`. Если параметр не задан, для Huge Pages используется разумное значение по умолчанию 2 MiB.

Значение `MEMORY_HUGE_PAGE_BYTES` задаётся как обычное C-выражение в байтах, чтобы библиотека могла использовать его без дополнительного парсинга:

```c
#define MEMORY_USE_HUGE_PAGES
#define MEMORY_HUGE_PAGE_BYTES (2ULL * 1024ULL * 1024ULL) /* 2 MiB */
```

```c
#define MEMORY_USE_HUGE_PAGES
#define MEMORY_HUGE_PAGE_BYTES (1ULL * 1024ULL * 1024ULL * 1024ULL) /* 1 GiB */
```

Для Transparent Huge Pages размер не задаётся явно:

```c
#define MEMORY_USE_TRANSPARENT_HUGE_PAGES
```

Если Huge Pages недоступны на текущей платформе, закончился пул HugeTLB-страниц или конкретный запрос не может быть выполнен выбранным способом, библиотека автоматически переходит к следующей разрешённой политике: например, к Transparent Huge Pages, выровненному heap или обычному heap. Такой fallback важен, чтобы оптимизация памяти не превращалась в причину отказа приложения там, где обычная память ещё доступна.

Выравнивание и Huge Pages — это не универсальное ускорение. Механизм Huge Pages может уменьшить количество обращений к таблицам страниц и улучшить поведение больших рабочих наборов, но также может увеличить расход памяти, усилить фрагментацию, добавить копирование при изменении размера и вызвать дополнительные задержки в ядре. Поэтому включать эти режимы нужно только после профильных тестов конкретного приложения и конкретной платформы.

`m_resize(...)` остаётся функцией высокого уровня. Его задача — проверить дескриптор, сохранить логический размер в `length`, поддержать строковые инварианты, применить флаги вроде `ZERO_NEW_MEMORY` и `RELEASE_UNUSED`, вызвать `mem_resize_calculate_allocation_bytes(...)`, затем передать физическое изменение памяти в `mem_resize_storage(...)`.

`m_resize(...)` и `m_del(...)` выражают разные намерения. `m_resize(desc,0,RELEASE_UNUSED)` очищает логический размер и возвращает резерв как resize-операция. `m_del(desc)` применяется, когда работа с текущим буфером закончена и хранилище нужно освободить независимо от текущей логической длины. Оба пути оставляют дескриптор инициализированным: тип элемента и string/data-режим сохраняются. Такое разделение позволяет развивать разные backend-ы памяти, не усложняя прикладной API.

## Поля дескриптора

Структура `memory` хранит всё состояние управляемого блока:

| Поле | Тип | Описание |
|---|---|---|
| `->single_element_size` | `size_t` | Размер одного элемента в байтах. Устанавливается один раз при инициализации дескриптора и далее не меняется |
| `->actually_allocated_bytes` | `size_t` | Полный объём байтов, реально зарезервированный аллокатором. Может быть больше, чем логическое содержимое дескриптора, из-за выравнивания, но для корректного непустого дескриптора должен покрывать текущие данные |
| `->length` | `size_t` | Текущее количество элементов в выделенном блоке |
| `->string_length` | `size_t` | Закэшированное количество видимых строковых элементов без завершающего нулевого элемента. В режиме данных всегда равно `0` |
| `->is_string` | `bool` | Флаг текущего режима. `true` означает строковый дескриптор, `false` означает обычные данные |
| `->data` | `void *` | Указатель на начало выделенного блока либо `NULL`, если памяти не выделено|

## Два режима работы дескрипторов

Дескриптор `memory` может использоваться в двух разных режимах. Текущее состояние хранится в `->is_string`, а публичные функции могут переключать этот флаг и поддерживать связанные метаданные. Режим выбирается явным использованием функций конвертации `m_to_string` или `m_to_data`, а не ручным редактированием полей структуры. Для явной ручной инициализации дескриптора в выражениях применяется `m_init(T)`, `m_init(T, MEMORY_DATA)` или `m_init(char, MEMORY_STRING)`. Для глобальных и статических инициализаторов применяется `m_init_static(T, ...)`.

Корректный дескриптор не может одновременно иметь `->length > 0` и `->data == NULL`. Публичные функции, которые валидируют состояние дескриптора, завершаются ошибкой на такой комбинации и не пытаются чинить её молча.

Подробности по строковому режиму смотрите в разделе [«Работа со строками»](#работа-со-строками), по бинарному — в [«Работа с данными (бинарный режим)»](#работа-с-данными-бинарный-режим). Операции, общие для обоих режимов, описаны в [«Операции, не зависящие от режима»](#операции-не-зависящие-от-режима).

## Работа с данными (бинарный режим)

В бинарном режиме дескриптор хранит произвольные байты или типизированные элементы. Такие функции работают с `->length` — общим количеством элементов — и никогда не анализируют содержимое на наличие строкового терминатора и не добавляют его автоматически.

### Обзор API бинарного режима

`m_copy(dest, src)` копирует содержимое одного дескриптора в другой. Оба дескриптора должны находиться в одном и том же режиме: строка копируется в строковый дескриптор, а data-дескриптор — в data-дескриптор.

`m_copy_buffer(dest, source_buffer_size_bytes, source_buffer)` заменяет содержимое data-дескриптора байтами из обычного внешнего буфера. Функция копирует ровно `source_buffer_size_bytes` байт и не пытается искать внутри них строковый терминатор.

`m_concat_data(dest, src)` дописывает содержимое одного data-дескриптора в конец другого. Функция работает только тогда, когда оба дескриптора уже находятся в режиме данных.

`m_concat_buffer(dest, source_buffer_size_bytes, source_buffer)` дописывает в data-дескриптор ровно `source_buffer_size_bytes` байт из внешнего буфера. Содержимое буфера воспринимается как обычные данные: нулевые байты не останавливают копирование и не имеют специального смысла.

`m_to_data(desc)` явно переводит строковый дескриптор в режим данных. В текущей реализации этот переход поддерживает только строковые дескрипторы с байтовым элементом (`->single_element_size == sizeof(char)`). Если строковый нуль-терминатор был последним логическим элементом, функция исключает его из `->length`, чтобы в логическом содержимом остались только полезные данные.

#### Пример 04. Типизированный data-дескриптор и self-aliased конкатенация

Проверяется тестом [`test_libmem_0000_04`](tests/src/test_libmem_0000.c#L110)

Иллюстрирует сразу три ключевые гарантии библиотеки:

* **Типизированное хранение.** При создании через `m_create(point,points)` библиотека запоминает `sizeof(point)`, а проверенный доступ через `m_data(point,...)` и `m_data_ro(point,...)` работает с массивом структур `point`, а не с неразмеченными байтами
* **Безопасный self-aliasing при росте хранилища.** Вызов `m_concat_data(mirror,mirror)` использует текущий буфер `mirror` одновременно как источник и как назначение. Исполняемый тест подбирает исходный размер так, чтобы операция расширила физический резерв: даже если внутренний `realloc(...)` переместит буфер, во второй половине результата должны сохраниться все исходные точки
* **Разделение чтения и записи.** `m_data` отдаёт `point *` для записи, `m_data_ro` — `const point *` для чтения. Разные функции доступа к одному и тому же дескриптору позволяют точечно ограничивать права кода, который работает с буфером

```c
#include "mem.h"

typedef struct { int x, y; } point;

int main(void)
{
	/* Исполняемый тест берёт один блок, чтобы self-append потребовал роста хранилища */
	const size_t point_count = MEMORY_BLOCK_BYTES / sizeof(point);

	m_create(point,points);
	if((TRIUMPH & m_resize(points,point_count)) == 0)
	{
		return(FAILURE);
	}

	/* Прямая запись через проверенный по типу указатель */
	point *p = m_data(point,points);
	for(size_t i = 0; i < points->length; ++i)
	{
		p[i] = (point){(int)i,(int)i};
	}

	/* Зеркальный дескриптор: копия, затем конкатенация собственного содержимого */
	m_create(point,mirror);
	if((TRIUMPH & m_copy(mirror,points)) == 0)
	{
		return(FAILURE);
	}

	if((TRIUMPH & m_concat_data(mirror,mirror)) == 0)
	{
		return(FAILURE);
	}

	/* Read-only представление для безопасного чтения */
	const point *view = m_data_ro(point,mirror);

	/* Первая и вторая половины view содержат один и тот же исходный массив точек */
	(void)view;

	m_del(points);
	m_del(mirror);

	return 0;
}
```

#### Пример 05. Сборка журнальной записи: data → string с повторным использованием резерва

Проверяется тестом [`test_libmem_0000_05`](tests/src/test_libmem_0000.c#L173)

Иллюстрирует ключевую особенность библиотеки — один и тот же дескриптор может последовательно работать в двух режимах: сначала как контейнер сырых байт, потом как полноценная строка с кэшированной длиной. В данном сценарии короткий префикс уже находится в выделенном блоке с запасным местом для нуль-терминатора, поэтому `m_to_string` измеряет видимый префикс, дописывает терминатор и переключает режим, сохраняя тот же физический буфер и тот же размер резерва

Это свойство относится к сценарию, где в текущем резерве уже хватает места под терминатор. Если data-буфер заполнил весь доступный резерв, `m_to_string` вправе расширить физическое хранилище, чтобы строка оставалась корректно завершённой

Сценарий типичен для сборки журнальных строк или сетевых сообщений: первая часть приходит из бинарного источника (поток, буфер фиксированного размера), а к ней нужно дописать форматированный «человеческий» хвост.

```c
m_create(char,log,MEMORY_DATA);

/* Фаза 1: data-режим — копируем и дописываем сырые байты */
if((TRIUMPH & m_copy_buffer(log,5,"GET /")) == 0)
{
	return(FAILURE);
}

if((TRIUMPH & m_concat_buffer(log,4,"api ")) == 0)
{
	return(FAILURE);
}

/* В этом коротком сообщении выделенный блок уже имеет место под терминатор.
   Исполняемый тест сохраняет log->data и log->actually_allocated_bytes,
   чтобы подтвердить повторное использование того же физического буфера */
if((TRIUMPH & m_to_string(log)) == 0)
{
	return(FAILURE);
}

/* Фаза 2: строковый режим — работают строковые операции с кэшем длины */
if((TRIUMPH & m_concat_literal(log,"200 OK")) == 0)
{
	return(FAILURE);
}

printf("%s\n",m_text(log)); /* "GET /api 200 OK" */
m_del(log);
```

Главная мысль примера: в показанном сценарии переход data → string сохраняет видимый префикс и, поскольку под терминатор уже есть свободный резерв, оставляет тот же физический буфер. Дальше с буфером работают функции, которые опираются на кэшированную `->string_length` и сами поддерживают терминатор

#### Пример 06. Повторное использование дескриптора после `m_del`

Проверяется тестом [`test_libmem_0000_06`](tests/src/test_libmem_0000.c#L218)

Дескриптор в `libmem` хранит указатель на принадлежащий ему буфер и метаданные этого буфера. После `m_del(...)` принадлежащий дескриптору буфер освобождается, указатель обнуляется, длины сбрасываются, а тип элемента и string/data-режим сохраняются. Сам дескриптор остаётся инициализированным объектом, поэтому его можно снова передать операции библиотеки, которая при необходимости выделит новый буфер

Эта гарантия не делает безопасным старый указатель на прежнее содержимое. Любой указатель, полученный из дескриптора до `m_del(...)`, становится недействительным после освобождения буфера. В этом примере повторно используется именно дескриптор `greeting`, а не указатель на строку `"alive"`

```c
m_create(char,greeting,MEMORY_STRING);

if((TRIUMPH & m_copy_literal(greeting,"alive")) == 0)
{
	return(FAILURE);
}

printf("%s\n",m_text(greeting)); /* "alive" */

m_del(greeting); /* буфер освобождён, дескриптор остался пустым строковым дескриптором */

/* Повторно используем дескриптор; указатель на его прежний буфер уже недействителен */
if((TRIUMPH & m_copy_literal(greeting,"reborn")) == 0)
{
	return(FAILURE);
}

printf("%s\n",m_text(greeting)); /* "reborn" */

m_del(greeting); /* парный m_del под повторно выделенный буфер обязателен */
```

Главная мысль примера: `m_del(...)` завершает жизнь текущего буфера, но сохраняет дескриптор пригодным для последующего нового содержимого того же типа и режима. Повторное выделение буфера по-прежнему требует последующего `m_del(...)`

### Конвертация data → string и обратно

#### Пример 07. Преобразование data-буфера с уже импортированным терминатором

Проверяется тестом [`test_libmem_0000_07`](tests/src/test_libmem_0000.c#L255)

В отличие от примера 05, здесь `m_copy_buffer(buffer,sizeof("abc"),"abc")` копирует в data-дескриптор весь массив строкового литерала: символы `a`, `b`, `c` и завершающий нулевой элемент. В data-режиме этот нуль пока является частью импортированных байт. После `m_to_string(buffer)` он распознаётся как строковый терминатор, поэтому `->string_length` получает значение `3`, а `->length` остаётся равной `sizeof("abc")`

```c
m_create(char,buffer);

/* sizeof("abc") включает завершающий нулевой байт в импортируемые данные */
if((TRIUMPH & m_copy_buffer(buffer,sizeof("abc"),"abc")) == 0)
{
	return(FAILURE);
}

/* Конвертация переиспользует импортированный терминатор и не увеличивает length */
if((TRIUMPH & m_to_string(buffer)) == 0)
{
	return(FAILURE);
}

/* Здесь buffer->is_string == true, buffer->string_length == 3
   и buffer->length == sizeof("abc") */
```

`m_to_string(buffer)` один раз измеряет видимый префикс в элементах, считая терминатором первый нулевой элемент. Если этот терминатор уже находится в логическом data-содержимом, как в данном примере, конвертация оставляет `->length` без изменения. Для непустого дескриптора без такого элемента функция при необходимости добавляет терминатор, а пустой дескриптор оставляет без выделения памяти. Дескриптор с `->length > 0` и `->data == NULL` считается неконсистентным и приводит к ошибке. Для data-режима также ожидается `->string_length == 0`; если низкоуровневый код оставил там устаревший кэш длины строки, конвертация завершится ошибкой вместо того, чтобы гадать, какому строковому состоянию верить

Обратное направление — `m_to_data(buffer)` возвращает строковый дескриптор в режим данных. Сейчас этот переход поддерживается только для строковых дескрипторов с байтовым элементом (`->single_element_size == sizeof(char)`). В строковом режиме нулевой терминатор хранится в том же буфере, что и текст, но остаётся служебным элементом: он нужен C-строкам для обозначения конца и не является частью полезных данных. Поэтому при переходе в data-режим библиотека убирает этот служебный элемент из логической длины. Если терминатор стоял последним логическим элементом, `->length` уменьшается на единицу. Например, строковый буфер `"abc"` обычно имеет `->length == 4`: три символа и завершающий нуль. После `m_to_data(buffer)` полезная нагрузка становится data-последовательностью из трёх элементов `a`, `b`, `c`, а нуль-терминатор больше не входит в логическое содержимое

## Работа со строками

В строковом режиме дескриптор может хранить обычную C-строку или строку с произвольной шириной символа, например `wchar_t`. Сразу после создания дескриптор может быть «пустой строкой» — память ещё не выделена, но он уже готов принимать строковые данные. Библиотека сама запоминает длину строки в поле `->string_length` (без учёта завершающего нуля) и при любой записи гарантирует, что в конце буфера всегда стоит ровно один нуль-терминатор `'\0'` или полностью заполненный нулями символ произвольной ширины. Терминатор и длину поддерживает сама библиотека — вручную их трогать не требуется.

### Обзор API строкового режима

`m_copy_fixed_string(dest, source_size_bytes, source)` полностью заменяет содержимое строкового дескриптора строкой фиксированного известного размера. `source_size_bytes` — это полный размер источника в байтах, включая завершающий нулевой элемент. Последний логический элемент источника уже должен быть нулевым терминатором, поэтому функция не ищет `'\0'` внутри буфера.

`m_copy_literal(dest, "text")` — удобная форма для функции `m_copy_fixed_string(...)` для использования со строковыми литералами. Размер литерала вычисляется автоматически через `sizeof`, поэтому его не нужно передавать вручную.

#### Пример 08. Копирование строкового литерала и строки фиксированного размера

Проверяется тестом [`test_libmem_0000_08`](tests/src/test_libmem_0000.c#L287)

Для строкового литерала `m_copy_literal(title,"hello")` автоматически вычисляет полный размер массива `sizeof("hello")`, включая завершающий нулевой элемент, и использует fixed-string семантику. Поэтому после вызова видимая длина равна `5`, а логическая длина дескриптора равна `sizeof("hello")`. Явный вызов `m_copy_fixed_string(title,sizeof("hello"),"hello")` должен получить то же строковое состояние

```c
/* Для литерала размер вместе с терминатором вычисляется автоматически */
if((TRIUMPH & m_copy_literal(title,"hello")) == 0)
{
	return(FAILURE);
}

/* Та же fixed-string операция с явно записанным размером */
if((TRIUMPH & m_copy_fixed_string(title,sizeof("hello"),"hello")) == 0)
{
	return(FAILURE);
}
```

Этот пример проверяет именно удобную форму для литералов. Поведение `m_copy_fixed_string(...)` для отдельного массива с известным размером и гарантированным последним терминатором показано в примере 11

`m_copy_string(dest, source_limit_bytes, source)` полностью заменяет содержимое строкового дескриптора видимой частью ограниченного строкового буфера. `source_limit_bytes` — это максимальное количество байт, внутри которого функция ищет первый нулевой элемент. В дескриптор копируется только видимый префикс.

`m_copy_string(dest, buf)` делает то же самое для обычной нуль-терминированной строки без заранее известной верхней границы. Такой вариант можно использовать только тогда, когда источник точно содержит нулевой терминатор.

Подробное правило выбора между `m_copy_fixed_string(...)`, `m_copy_literal(...)` и `m_copy_string(...)` описано в разделе [«Когда использовать `m_copy_fixed_string`, а когда `m_copy_string`»](#когда-использовать-m_copy_fixed_string-а-когда-m_copy_string).

`m_finalize_string(dest, len[, flags])` завершает прямую запись в строковый буфер. Функция фиксирует видимую длину `len` в `->string_length` и при необходимости гарантирует нулевой терминатор на новой границе строки.

Если флаг не указан, используется поведение `WRITE_TERMINATOR_IF_MISSING`: библиотека проверяет элемент на позиции `len` и записывает туда нулевой терминатор только тогда, когда его там ещё нет. Явный флаг `WRITE_TERMINATOR_ALWAYS` заставляет библиотеку записать нулевой терминатор в позицию `len` без проверки. Оба варианта оставляют дескриптор в корректном строковом состоянии; разница только в том, нужно ли безусловно перезаписывать пограничный элемент.

`m_formatted_string(dest, fmt, ...)` полностью заменяет содержимое строкового дескриптора результатом printf-style форматирования, когда `fmt` не равен `NULL`. По смыслу функция близка к `sprintf`, только `dest` здесь не сырой `char *`-буфер, а строковый дескриптор `libmem`, который сам управляет памятью, длиной и терминатором. Функция поддерживает строковые дескрипторы с элементами ширины `char` и `wchar_t`.

#### Пример 09. Форматированная строка

Проверяется тестом [`test_libmem_0000_09`](tests/src/test_libmem_0000.c#L319)

Форматная строка и аргументы обрабатываются так же, как в printf-style вызове, но результат сразу становится корректным содержимым строкового дескриптора. В этом примере `%u` преобразует число `7U` в имя файла `"file-7.txt"`; после успешной операции `title->string_length` равна видимой длине строки, а `title->length` также включает завершающий нулевой элемент

```c
m_create(char,title,MEMORY_STRING);

if((TRIUMPH & m_formatted_string(title,"file-%u.txt",7U)) == 0)
{
	return(FAILURE);
}

printf("%s\n",m_text(title)); /* "file-7.txt" */
m_del(title);
```

`m_concat_fixed_string(dest, source_size_bytes, source)` дописывает к строковому дескриптору строку фиксированного известного размера. `source_size_bytes` — это полный размер источника в байтах, включая завершающий нулевой элемент. Последний логический элемент источника уже должен быть нулевым терминатором.

`m_concat_literal(dest, "text")` — удобная форма вызова функции `m_concat_fixed_string(...)` для строковых литералов. Размер литерала вычисляется автоматически через `sizeof`.

`m_concat_strings(dest, src)` дописывает один строковый дескриптор в другой. Функция использует уже закэшированные `->string_length` у обоих дескрипторов, поэтому ей не нужно заново искать терминаторы.

`m_concat_string(dest, source_limit_bytes, source)` дописывает видимую часть ограниченного строкового буфера. `source_limit_bytes` — это максимальное количество байт, внутри которого функция ищет первый нулевой элемент. В дескриптор дописывается только видимый префикс.

`m_concat_string(dest, buf)` дописывает обычную нуль-терминированную строку без заранее известной верхней границы. Такой вариант подходит только для источников, в которых нулевой терминатор гарантирован.

**Все функции строковой конкатенации** записывают новые данные поверх старого терминатора `dest`, а затем ставят один новый терминатор в конец результата. Старый терминатор не остаётся внутри строки. Например, `m_concat_strings(dest, src)` для `"abc"` и `"XYZ"` даёт `"abcXYZ\0"`, а не `"abc\0XYZ\0"`. Точно так же `m_concat_literal(dest, "-done")` превращает `"task\0"` в `"task-done\0"`.

`m_string_truncate(dest, len)` обрезает видимую строку до `len` элементов и записывает терминатор на новой границе. Общий `->length` дескриптора при этом не уменьшается.

`m_string(desc)` возвращает мягкое представление строки только для чтения. Оно работает со строковыми дескрипторами любой ширины элемента и в некорректных случаях возвращает безопасный пустой буфер вместо `NULL`. Подробности описаны в разделе [«Безопасный строковый доступ»](#безопасный-строковый-доступ).

`m_text(desc)` — байтовая обёртка над `m_string(...)` для обычных `char`-строк. В такой строке один элемент дескриптора занимает один байт, как в привычной C-строке `"text"`. Функция возвращает результат как `const char *`, когда вызывающему коду нужен указатель на обычную C-строку. Подробности описаны в разделе [«Безопасный строковый доступ»](#безопасный-строковый-доступ).

`m_string_length(desc, &len)` получает видимую длину строки в элементах. Для строкового дескриптора функция возвращает закэшированное `->string_length`. Для data-дескриптора она ищет первый нулевой элемент только внутри логического содержимого дескриптора — то есть среди тех элементов, которые уже считаются частью данных, и не читает память дальше.

`m_to_string(desc)` явно переводит дескриптор из режима данных в строковый режим и кэширует видимую длину. Пустой дескриптор остаётся строковым, но память для него не выделяется. Подробнее этот переход описан в разделе [«Конвертация data → string и обратно»](#конвертация-data--string-и-обратно).

### Прямая запись через `m_data`

Исключение из правила «терминатор и длину поддерживает библиотека» — это прямое редактирование буфера через `m_data(...)`. После такой записи дескриптор нужно корректно терминировать самостоятельно. Какие функции для этого использовать, описано ниже в разделе [«Какую функцию выбрать после прямой записи»](#какую-функцию-выбрать-после-прямой-записи):

#### Пример 10. Прямая запись через `m_data` и фиксация строкового состояния

Проверяется тестом [`test_libmem_0000_10`](tests/src/test_libmem_0000.c#L346)

Строковый дескриптор сначала содержит `"alphabet"`. При прямой записи код заменяет только первые пять символов, поэтому сразу после записи в буфере всё ещё находится продолжение старой строки. Вызов `m_finalize_string(buffer,5)` ставит терминатор вместо прежней `'b'`, обновляет `->string_length` до `5`, но оставляет `->length == sizeof("alphabet")`: сокращается видимая строка, а не логическая длина уже подготовленного буфера

```c
m_create(char,buffer,MEMORY_STRING);

if((TRIUMPH & m_copy_literal(buffer,"alphabet")) == 0)
{
	return(FAILURE);
}

char *writable = m_data(char,buffer);
if(writable == NULL)
{
	return(FAILURE);
}

/* Прямой доступ заменяет только видимый префикс старой строки */
writable[0] = 'A';
writable[1] = 'L';
writable[2] = 'P';
writable[3] = 'H';
writable[4] = 'A';

/* Финализация делает видимой строку "ALPHA" и сохраняет прежний length */
if((TRIUMPH & m_finalize_string(buffer,5)) == 0)
{
	return(FAILURE);
}

printf("%s\n",m_text(buffer)); /* "ALPHA" */
m_del(buffer);
```

> **Важно:** любая работа с буфером строкового дескриптора через `m_data(...)` **обязательно** должна завершаться вызовом одной из двух функций — `m_finalize_string(...)` или `m_string_truncate(...)`. Иначе нарушаются инварианты строкового режима, и дальнейшие строковые операции либо отклонят дескриптор, либо вернут некорректный результат.

#### Что именно ломается

Корректный строковый дескриптор поддерживает несколько связанных гарантий одновременно:

1. **`->is_string == true`** — флаг строкового режима.
2. **`->string_length` совпадает с реальной видимой длиной** — то есть с количеством элементов в буфере до первого нулевого терминатора.
3. **В позиции `->data[->string_length]` физически стоит нулевой терминатор** — символ `'\0'` для байтовых строк или элемент, у которого все байты равны нулю, для широких строк.
4. **`->string_length < ->length`** — в общей длине всегда есть место под терминатор.

После прямой записи через `m_data(...)` все эти гарантии библиотека **уже не отслеживает автоматически**, потому что запись в буфер выполняла не она, а прикладной код. Возможные сценарии повреждения:

- **Видимая длина стала короче, но `->string_length` не обновлён.** Например, физически в буфере уже лежит `"ALPHA\0bet"`, но `->string_length` всё ещё равен `8` от старой строки `"alphabet"`. Функции вроде `m_string_length(...)` вернут устаревшее значение `8`, `m_text(...)` пройдёт мимо нового `'\0'` в середине, а `m_concat_string(...)` начнёт дописывать данные в неправильную позицию.
- **Видимая длина стала длиннее, но терминатор не передвинут.** Если строка расширялась и в буфер были записаны символы за старым `'\0'`, кешированный `->string_length` всё равно ссылается на старую границу, и новая часть строки не попадёт ни в одну строковую операцию.
- **Случайно затёрт терминатор.** Если в позиции `->data[->string_length]` оказался не нулевой элемент, нарушается гарантия №3. Любая функция, которая полагается на наличие терминатора, прочитает за пределы видимой строки.
- **Записан `'\0'` внутрь видимой части.** Часть символов «исчезает» с точки зрения строковых операций, потому что они останавливаются на первом нуле, а кешированный `->string_length` об этом не знает.

#### Что библиотека проверяет, а что нет

Здесь важно различать два уровня проверок.

**Что проверяется на каждом строковом вызове.** Публичные функции (`m_concat_strings`, `m_copy`, `m_resize` в строковом режиме и др.) перед работой проверяют только согласованность *метаданных* дескриптора:

- `->length == 0` подразумевает `->string_length == 0`;
- для непустого буфера `->string_length < ->length` (то есть в общем размере есть место под терминатор).

Если хотя бы одна проверка не выполняется, функция возвращает `FAILURE` и пишет в stderr сообщение `Destination string descriptor is inconsistent` или `Source string descriptor is inconsistent`.

**Что НЕ проверяется ни в одной публичной функции.** По соображениям производительности библиотека **не сканирует** буфер и **никогда не проверяет**, что в позиции `->data[->string_length]` действительно лежит `'\0'`. Кешированный `->string_length` — главный источник правды о видимой длине строки, и библиотека ему доверяет всегда. Если через `m_data(...)` записаны данные так, что физический терминатор не совпадает с кешем (например, `'\0'` передвинут влево или вправо без обновления `->string_length`), все функции просто отработают по устаревшему кешу и дадут логически неверный результат: лишние или потерянные символы, мусор после конкатенации, обрезанная строка в `m_text(...)` и т. п.

Несколько функций всё-таки заглядывают в буфер на наличие нулевого элемента, но **не для валидации инварианта** `->data[->string_length] == '\0'`, а для собственных нужд:

- `m_finalize_string(buffer, written_length)` смотрит в позицию `->data[written_length]` (параметр от вызывающего кода, а не текущий `->string_length`), чтобы решить, надо ли дописывать терминатор;
- `m_string_truncate(buffer, len)` тоже смотрит в `->data[len]` (новую границу), чтобы избежать лишней записи, если терминатор уже стоит;
- `m_to_data(buffer)` для поддерживаемых байтовых строковых дескрипторов смотрит в `->data[->length - 1]` (самый последний логический элемент) и, если там нулевой элемент, исключает его из `->length`.

Иными словами: библиотека защищает прикладной код от грубо испорченных метаданных, но не от рассинхронизации между метаданными и содержимым буфера. Эту синхронизацию обязан поддерживать прикладной код — через `m_finalize_string(...)` или `m_string_truncate(...)` сразу после прямой записи.

#### Какую функцию выбрать после прямой записи

- `m_finalize_string(buffer, len)` — когда точная видимая длина `len` известна, но нет уверенности, стоит ли уже терминатор в `buffer[len]`. По умолчанию (`WRITE_TERMINATOR_IF_MISSING`) функция допишет `'\0'` только если его там нет. С флагом `WRITE_TERMINATOR_ALWAYS` — перезапишет в любом случае.
- `m_string_truncate(buffer, len)` — когда нужно явно «обрезать» видимую строку до `len` элементов, не глядя на содержимое за этой границей. Функция всегда записывает терминатор на `buffer[len]`.

В обоих случаях после вызова дескриптор снова валиден, `->string_length` обновлён и любые строковые операции на нём работают корректно.

### Когда использовать `m_copy_fixed_string`, а когда `m_copy_string`

Эти две функции внешне похожи, но имеют принципиально разную семантику работы с исходной строкой. От правильного выбора зависит безопасность программы.

#### `m_copy_fixed_string` — режим доверия

В этом режиме библиотека **не проверяет** исходную строку и **не ищет** в ней нуль-терминатор. Она просто доверяет переданному размеру и считает, что последний элемент по указанному размеру уже является `'\0'`. Это самый быстрый путь, но он требует гарантии того, что:

- Исходная строка действительно нуль-терминирована именно **в самом конце** буфера (по указанному размеру).
- В строке нет «лишних» нулей внутри — но если они есть, библиотека всё равно скопирует весь блок целиком, не обрезая его.

Подходит для массивов с известным размером, где терминатор гарантированно стоит последним.

#### Пример 11. Копирование строки фиксированного размера

Проверяется тестом [`test_libmem_0000_11`](tests/src/test_libmem_0000.c#L391)

```c
const char text[] = {'H','e','l','l','o','\0'};
m_copy_fixed_string(dest, sizeof(text), text);
```

При **отсутствии уверенности** в том, что нуль-терминатор стоит именно последним символом, эта функция **не подходит**. Подходящая альтернатива — [`m_copy_string`](#m_copy_string--режим-поиска-терминатора): она сама просканирует исходный буфер в поиске `'\0'`, при этом поиск можно ограничить максимальным размером, чтобы не выйти за границы, если терминатор так и не будет найден.

#### `m_copy_literal` — удобная обёртка для строковых литералов

Это синтаксический сахар поверх `m_copy_fixed_string` специально для строковых литералов. Размер вычисляется компилятором автоматически через `sizeof`, указывать его вручную не требуется:

```c
m_copy_literal(dest, "Hello world");
// эквивалентно:
// m_copy_fixed_string(dest, sizeof("Hello world"), "Hello world");
```

Этот макрос предпочтителен везде, где копируется именно строковый литерал — он короче и исключает риск ошибиться в размере.

#### `m_copy_string` — режим поиска терминатора

Эта функция активно ищет нуль-терминатор в исходном буфере и поддерживает два режима работы:

1. **С ограничением** — `m_copy_string(dest, source_limit_bytes, source)`: библиотека просканирует первые `source_limit_bytes` байт исходной строки в поиске `'\0'`. Если терминатор найден раньше — копируется только видимая часть до него. Если не найден в пределах лимита — копируется ровно `source_limit_bytes` байт. Это безопасный выбор, когда исходная строка может быть как нуль-терминированной, так и нет.

2. **Без ограничений** — `m_copy_string(dest, buf)`: библиотека сканирует исходную строку до первого `'\0'` без верхней границы. Этот режим применим только при абсолютной уверенности в том, что строка **точно нуль-терминирована** где-то в памяти, иначе будет выход за границы буфера.

#### Краткое правило выбора

Если источник — строковый литерал в коде, например `"text"`, используйте `m_copy_literal(dest, "text")`. Это самый простой вариант: размер литерала будет вычислен автоматически.

Если источник — массив с фиксированным размером, и `'\0'` гарантированно стоит последним логическим элементом, используйте `m_copy_fixed_string(dest, source_size_bytes, source)`. Такой вариант не тратит время на поиск терминатора.

Если известна верхняя граница буфера, но `'\0'` может оказаться раньше или вообще отсутствовать, используйте `m_copy_string(dest, source_limit_bytes, source)`. Это безопасный вариант для внешних данных: поиск терминатора не выйдет за переданный лимит.

Если источник — точно нуль-терминированная C-строка без заранее известной верхней границы, используйте `m_copy_string(dest, buf)`. Этот вариант требует уверенности, что терминатор действительно есть.

### Когда использовать `m_concat_fixed_string`, а когда `m_concat_string`

По аналогии с парой `m_copy_fixed_string` / `m_copy_string`, для конкатенации тоже есть выбор между «режимом доверия» и «режимом поиска терминатора». Разница только в том, что новые данные дописываются к существующей видимой строке, а не заменяют её целиком.

#### `m_concat_fixed_string` — режим доверия

Библиотека **не проверяет** дописываемую строку и **не ищет** в ней нуль-терминатор. Она просто доверяет переданному размеру и считает, что последний элемент по указанному размеру уже является `'\0'`. Это самый быстрый путь, но он требует гарантии того, что:

- Дописываемая строка действительно нуль-терминирована именно **в самом конце** буфера (по указанному размеру).
- В строке нет «лишних» нулей внутри — но если они есть, библиотека всё равно припишет весь блок целиком, не обрезая его.

Подходит для массивов с известным размером, где терминатор гарантированно стоит последним.

#### Пример 12. Добавление строки фиксированного размера

Проверяется тестом [`test_libmem_0000_12`](tests/src/test_libmem_0000.c#L420)

```c
const char suffix[] = {'-','e','n','d','\0'};
m_concat_fixed_string(dest, sizeof(suffix), suffix);
```

При **отсутствии уверенности** в том, что нуль-терминатор стоит именно последним символом, эта функция **не подходит**. Подходящая альтернатива — [`m_concat_string`](#m_concat_string--режим-поиска-терминатора): она сама просканирует дописываемый буфер в поиске `'\0'`, при этом поиск можно ограничить максимальным размером, чтобы не выйти за границы, если терминатор так и не будет найден.

Это синтаксический сахар поверх `m_concat_fixed_string` специально для строковых литералов. Размер вычисляется компилятором автоматически через `sizeof`, указывать его вручную не требуется:

#### Пример 13. Добавление строкового литерала

Проверяется тестом [`test_libmem_0000_13`](tests/src/test_libmem_0000.c#L450)

```c

// эквивалентно:
// m_concat_fixed_string(dest, sizeof("-suffix"), "-suffix");
```

Этот макрос предпочтителен везде, где дописывается именно строковый литерал — он короче и исключает риск ошибиться в размере.

#### `m_concat_string` — режим поиска терминатора

Эта функция активно ищет нуль-терминатор в дописываемом буфере и поддерживает два режима работы:

1. **С ограничением** — `m_concat_string(dest, source_limit_bytes, source)`: библиотека просканирует первые `source_limit_bytes` байт исходной строки в поиске `'\0'`. Если терминатор найден раньше — приписывается только видимая часть до него. Если не найден в пределах лимита — приписывается ровно `source_limit_bytes` байт. Это безопасный выбор, когда исходная строка может быть как нуль-терминированной, так и нет.

2. **Без ограничений** — `m_concat_string(dest, buf)`: библиотека сканирует исходную строку до первого `'\0'` без верхней границы. Этот режим применим только при абсолютной уверенности в том, что строка **точно нуль-терминирована** где-то в памяти, иначе будет выход за границы буфера.

#### `m_concat_strings` — конкатенация двух дескрипторов

Эта функция дописывает содержимое одного строкового **дескриптора** в другой. Поскольку оба дескриптора уже хранят кешированную длину `->string_length`, никакого поиска `'\0'` не требуется и операция выполняется максимально эффективно. Оба дескриптора должны быть в строковом режиме.

#### Краткое правило выбора

Если дописываемый источник — строковый литерал в коде, например `"text"`, используйте `m_concat_literal(dest, "text")`. Размер литерала будет вычислен автоматически.

Если источник — массив с фиксированным размером, и `'\0'` гарантированно стоит последним логическим элементом, используйте `m_concat_fixed_string(dest, source_size_bytes, source)`. Функция доверяет этому контракту и не ищет терминатор внутри буфера.

Если известна верхняя граница буфера, но `'\0'` может оказаться раньше или вообще отсутствовать, используйте `m_concat_string(dest, source_limit_bytes, source)`. Функция допишет только видимый префикс в пределах `source_limit_bytes` байт.

Если источник — точно нуль-терминированная C-строка без заранее известной верхней границы, используйте `m_concat_string(dest, buf)`. Этот вариант требует уверенности, что терминатор действительно есть.

Если источник — другой строковый дескриптор `libmem`, используйте `m_concat_strings(dest, src)`. Функция возьмёт длину из кеша `->string_length` и не будет сканировать буфер.

### Контракт строкового дескриптора

Для плотно упакованной строки `->string_length` обычно на единицу меньше, чем `->length`. Это нормальная ситуация: `->string_length` считает только видимые символы, а в `->length` входит ещё и завершающий нулевой элемент.

Но равенство `->length == ->string_length + 1` не является обязательным инвариантом для строкового режима. Строковый дескриптор может иметь логический размер заметно больше видимой строки, если код заранее зарезервировал место под будущую запись или конкатенацию.

Например, после копирования строки `"abc"` дескриптор обычно имеет `->string_length == 3` и `->length == 4`. Если затем вызвать `m_resize(desc,64)`, видимая строка останется той же самой, то есть `->string_length` останется равным `3`, а `->length` станет равным `64`. Это означает не появление новой видимой строки, а только то, что дескриптор теперь логически вмещает больше элементов и готов к дальнейшему добавлению данных в конец без немедленного нового расширения.

### Хелпер конкатенации строк

#### Пример 14. Конкатенация строковых дескрипторов

Проверяется тестом [`test_libmem_0000_14`](tests/src/test_libmem_0000.c#L541)

Полный пример с конкатенацией двух строковых дескрипторов через `m_concat_strings(...)`.

Важно: оба дескриптора создаются сразу в строковом режиме (`MEMORY_STRING`), а после прямой записи в буфер обязательно должна быть вызвана функция `m_finalize_string(...)`.

Здесь для прямой записи используется `snprintf(...)`, потому что она сразу сообщает длину получившейся видимой строки без учёта завершающего `'\0'`. Это значение передаётся в `m_finalize_string(...)`, чтобы строковый дескриптор получил актуальный `->string_length` перед вызовом `m_concat_strings(...)`.

```c
#include "mem.h"
#include <stdio.h>

int main(void)
{
	m_create(char,first,MEMORY_STRING);
	m_create(char,second,MEMORY_STRING);

	/* Резервируем записываемую ёмкость, включая место под нуль-терминатор */
	if((TRIUMPH & m_resize(first,16)) == 0)
	{
		return(FAILURE);
	}

	if((TRIUMPH & m_resize(second,16)) == 0)
	{
		return(FAILURE);
	}

	/* Записываем строки через m_raw_data().
	   snprintf возвращает длину видимой строки без учёта '\0',
	   поэтому это значение сразу годится для m_finalize_string */
	char *first_buf = m_raw_data(first);
	char *second_buf = m_raw_data(second);
	if(first_buf == NULL || second_buf == NULL)
	{
		return(FAILURE);
	}

	int first_written = snprintf(first_buf,first->length,"Hello");
	if(first_written < 0 || (size_t)first_written >= first->length)
	{
		return(FAILURE);
	}

	int second_written = snprintf(second_buf,second->length," world!");
	if(second_written < 0 || (size_t)second_written >= second->length)
	{
		return(FAILURE);
	}

	/* Зафиксировать видимую длину после прямой записи: иначе ->string_length
	   останется равным 0, и m_concat_strings отработает по устаревшему кешу */
	if((TRIUMPH & m_finalize_string(first,(size_t)first_written)) == 0)
	{
		return(FAILURE);
	}

	if((TRIUMPH & m_finalize_string(second,(size_t)second_written)) == 0)
	{
		return(FAILURE);
	}

	if((TRIUMPH & m_concat_strings(first,second)) == 0)
	{
		return(FAILURE);
	}

	/* Выводим результат конкатенации двух финализированных строковых дескрипторов */
	/* m_text(...) — мягкая функция доступа только для чтения для байтовых строковых дескрипторов:
	   проверяет инварианты строкового режима и никогда не возвращает NULL,
	   что делает его безопаснее, чем m_raw_data_ro(...) */
	printf("%s\n",m_text(first)); /* Напечатает "Hello world!" */

	m_del(first);
	m_del(second);
	return 0;
}
```

### Безопасный строковый доступ

`mem_string` и макрос `m_string(...)` дают мягкий доступ только для чтения к строковому дескриптору с любой шириной элемента. Функция не ищет терминатор, не пересчитывает видимую длину и не меняет состояние дескриптора. Она проверяет только самые грубые инварианты строкового дескриптора и в остальном доверяет закэшированному `->string_length`. При грубых нарушениях контракта функция пишет сообщение об ошибке и возвращает не `NULL`, а общий безопасный пустой буфер, заранее заполненный нулями. Такой результат можно читать как пустую строку, но его нельзя использовать для записи.

`m_text(...)` — это байтовая обёртка над `m_string(...)`. Она нужна для тех мест, где вызывающий код уже знает, что работает именно с байтовым строковым дескриптором, и хочет получить `const char *`, а не обобщённый `const void *`. Дополнительных проверок во время выполнения макрос не добавляет и полностью сохраняет мягкий контракт `m_string(...)`.

Записываемый строковый доступ делается явно. `m_data(char,...)` применяется, когда нужен проверенный записываемый указатель без смены режима; после прямой записи в строковый дескриптор обязательно следует вызов `m_finalize_string(...)`, фиксирующий видимую длину. `m_raw_data(...)` применяется тогда, когда нужен именно сырой записываемый указатель и состояние дескриптора уже известно и доверено вызывающему коду.

#### Пример 15. Безопасное чтение строки через `m_text`

Проверяется тестом [`test_libmem_0000_15`](tests/src/test_libmem_0000.c#L625)

```c
#include "mem.h"
#include <stdio.h>

int main(void)
{
	m_create(char,buffer,MEMORY_STRING);
	m_create(char,scratch,MEMORY_STRING);
	size_t scratch_length = 0;

	if((TRIUMPH & m_resize(buffer,32,ZERO_NEW_MEMORY)) == 0)
	{
		return(FAILURE);
	}

	/* Получаем записываемое представление после m_resize, который мог переместить буфер */
	char *writable = m_data(char,buffer);
	if(writable == NULL)
	{
		return(FAILURE);
	}

	int written = snprintf(writable,buffer->length,"Hello world!");
	if(written < 0 || (size_t)written >= buffer->length)
	{
		return(FAILURE);
	}

	if((TRIUMPH & m_finalize_string(buffer,(size_t)written)) == 0)
	{
		return(FAILURE);
	}

	/* Указатель только для чтения никогда не равен NULL */
	const char *view = m_text(buffer);
	printf("%s\n",view); /* Напечатает "Hello world!" */

	/* Даже пустые инициализированные строковые дескрипторы дают пустое read-only представление */
	const char *scratch_view = m_text(scratch);
	printf("scratch text: \"%s\"\n",scratch_view); /* Напечатает scratch text: "" */

	if((TRIUMPH & m_string_length(scratch,&scratch_length)) == 0)
	{
		return(FAILURE);
	}

	printf("scratch length: %zu\n",scratch_length);

	m_del(buffer);
	m_del(scratch);
	return 0;
}
```

### Форматированные строки

`m_formatted_string(destination,format,...)` строит новую строку внутри уже строкового дескриптора по правилам `printf`-style форматирования. При ненулевом `format` старое видимое содержимое `destination` полностью заменяется результатом форматирования, а `->string_length` обновляется автоматически.

`m_formatted_string(...)` выбирает способ форматирования по размеру одного элемента в `destination`: `sizeof(char)` обрабатывается через `vsnprintf`, `sizeof(wchar_t)` — через `vswprintf`. Настоящий C-тип строки библиотека не хранит, поэтому другие размеры элемента эта функция сейчас отклоняет.

`format == NULL` считается пустым входным значением потока, не приводит к ошибке и оставляет `destination` без изменений. Форматная строка не должна указывать внутрь собственного буфера `destination`: эта операция заменяет содержимое дескриптора и сейчас не является self-aliasing операцией. Это ограничение — исключение из общего правила библиотеки, где self-aliasing должен обрабатываться безопасно. В будущем поведение `m_formatted_string(...)` должно быть приведено к этому стандартному правилу.

#### Пример 16. Форматированное сообщение

Проверяется тестом [`test_libmem_0000_16`](tests/src/test_libmem_0000.c#L653)

```c
#include "mem.h"
#include <stdio.h>

int main(void)
{
	m_create(char,message,MEMORY_STRING);

	const char *name = "archive.tar";
	const size_t size = 4096;

	if((TRIUMPH & m_formatted_string(message,"File %s: %zu bytes",name,size)) == 0)
	{
		m_del(message);
		return(FAILURE);
	}

	printf("%s\n",m_text(message));

	m_del(message);
	return 0;
}
```

### Строковые данные с заранее известной длиной

Иногда строка приходит не как гарантированно нуль-терминированная C-строка, а как буфер с известной границей: поле из файла, часть сетевого пакета, временный рабочий буфер. В таких случаях размер лучше передавать явно. Так библиотека не будет читать память за пределами известного буфера, даже если нулевой терминатор в источнике отсутствует или стоит не в конце.

- Для обычного байтового буфера размер задаётся как `m_resize(buffer,data_size_bytes)`.
- Для строкового буфера нужно место под завершающий нуль: `m_resize(buffer,visible_length + 1)`.
- `m_data(char,buffer)` даёт записываемый указатель с проверкой дескриптора и размера элемента. Это вариант для обычного кода, где повреждённый дескриптор должен быть замечен сразу.
- `m_raw_data(buffer)` даёт указатель с минимальными проверками состояния дескриптора, но без проверки типа элемента. Этот вариант подходит только для кода, который уже доверяет состоянию дескриптора и сам поддерживает строковые инварианты.
- После прямой записи в строковый дескриптор вызывается `m_finalize_string(buffer,written_length)`. Функция запоминает видимую длину строки и гарантирует терминатор на новой границе.
- Если источник уже лежит в буфере с известной верхней границей чтения, используется `m_copy_string(destination,source_limit_bytes,source)`. В дескриптор попадёт только видимая часть источника, а поиск `'\0'` не выйдет за пределы `source_limit_bytes` байт.
- Если терминатор нужно записать без проверки текущего содержимого, используется форма `m_finalize_string(buffer,written_length,WRITE_TERMINATOR_ALWAYS)`. Обычная форма `m_finalize_string(buffer,written_length)` записывает терминатор только тогда, когда его ещё нет.

#### Пример 17. Копирование и добавление строк из ограниченных буферов

#### Пример 18. Прямая запись в заранее выделенный строковый буфер

Проверяется тестом [`test_libmem_0000_18`](tests/src/test_libmem_0000.c#L719)

Этот пример показывает прямую запись в заранее выделенный строковый буфер. `memcpy(...)` копирует строку `"draft"` вместе с уже готовым завершающим `'\0'`. После прямой записи `m_finalize_string(...)` видит терминатор на ожидаемой границе, фиксирует видимую длину и возвращает дескриптор в согласованное строковое состояние:

```c
m_create(char,title,MEMORY_STRING);
const char draft[] = "draft";

if((TRIUMPH & m_resize(title,sizeof(draft))) == 0)
{
	return(FAILURE);
}

char *title_view = m_data(char,title);
if(title_view == NULL)
{
	return(FAILURE);
}

memcpy(title_view,draft,sizeof(draft));

if((TRIUMPH & m_finalize_string(title,sizeof(draft) - 1U)) == 0)
{
	return(FAILURE);
}
```

### Массивы строковых дескрипторов

`m_string_array_append(...)` нужен для случая, когда один дескриптор хранит не одну строку, а список строк. Корневой дескриптор создаётся как массив элементов `memory`, а каждая добавленная строка становится отдельным вложенным строковым дескриптором.

Такой массив удобно использовать для небольших списков имён, строк результата, частей сообщения или путей. Корневой дескриптор остаётся обычным data-дескриптором, а строки внутри него остаются полноценными строковыми дескрипторами `libmem`.

`m_string_array_append(array, element_type, source)` добавляет строку из обычного нуль-терминированного источника. Размер источника отдельно передавать не нужно.

`m_string_array_append(array, element_type, source_limit_bytes, source)` добавляет строку из буфера с известной верхней границей чтения. Библиотека ищет нулевой терминатор только внутри первых `source_limit_bytes` байт и копирует в новый элемент видимую часть источника.

`m_string_array_foreach(array,item)` обходит уже добавленные строки. На каждой итерации `item` — это `memory *` на вложенный строковый дескриптор.

`m_array_del(array)` освобождает массив вложенных дескрипторов: сначала очищает каждую строку внутри массива, затем очищает сам корневой дескриптор. Для массивов, созданных через `m_string_array_append(...)`, это правильный способ завершить работу.

#### Пример 19. Добавление строк в массив строковых дескрипторов

Проверяется тестом [`test_libmem_0000_19`](tests/src/test_libmem_0000.c#L761)

Самый простой вариант — добавление обычных нуль-терминированных строк:

```c
m_create(memory,names);

if((TRIUMPH & m_string_array_append(names,char,"delta")) == 0)
{
	return(FAILURE);
}

if((TRIUMPH & m_string_array_append(names,char,"epsilon")) == 0)
{
	return(FAILURE);
}

if((TRIUMPH & m_array_del(names)) == 0)
{
	return(FAILURE);
}
```

Если источник лежит в буфере с известной верхней границей, используется форма с размером. В новый элемент попадёт только видимая часть до первого `'\0'` или до конца указанного диапазона:

```c
const char source[] = {'z','e','t','a','\0','x'};

m_create(memory,names);

if((TRIUMPH & m_string_array_append(names,char,sizeof(source),source)) == 0)
{
	return(FAILURE);
}

if((TRIUMPH & m_array_del(names)) == 0)
{
	return(FAILURE);
}
```

Для обхода массива применяется `m_string_array_foreach(array,item)`. Макрос сам получает указатель на первый вложенный дескриптор и на каждой итерации даёт переменную `memory *item`. В теле цикла нельзя изменять размер или удалять корневой массив, потому что это может сделать текущий указатель недействительным.

#### Пример 20. Обход массива строковых дескрипторов

Проверяется тестом [`test_libmem_0000_20`](tests/src/test_libmem_0000.c#L846)

Пример добавляет три строки и печатает их все:

```c
#include "mem.h"
#include <stdio.h>

int main(void)
{
	m_create(memory,names);

	if((TRIUMPH & m_string_array_append(names,char,"alpha")) == 0)
	{
		return(FAILURE);
	}

	if((TRIUMPH & m_string_array_append(names,char,"beta")) == 0)
	{
		return(FAILURE);
	}

	if((TRIUMPH & m_string_array_append(names,char,"gamma")) == 0)
	{
		return(FAILURE);
	}

	m_string_array_foreach(names,item)
	{
		printf("%s\n",m_text(item));
	}

	if((TRIUMPH & m_array_del(names)) == 0)
	{
		return(FAILURE);
	}

	return 0;
}
```

Освобождать такой массив нужно через `m_array_del(...)`, а не через обычный `m_del(...)`. Эта функция сначала вызывает `m_del(...)` для каждой вложенной строки, а затем очищает сам корневой дескриптор.

### Ограничения и гарантии строкового режима

- **Произвольная ширина элемента.** Строки могут храниться в дескрипторах любого ненулевого `->single_element_size`: `char`, `signed char`, `unsigned char`, `char8_t`, `wchar_t`, `char16_t`, `char32_t`, а также целочисленные типы хранения `uint8_t`, `uint16_t`, `uint32_t`. Терминатором считается элемент, все байты которого равны нулю. Все строковые алгоритмы описываются в терминах целых элементов, поэтому единственное байтовое ограничение — у `m_formatted_string(...)`, которая поддерживает только `sizeof(char)` и `sizeof(wchar_t)`
- **Безопасный self-aliasing — обязательная гарантия.** Источник, указывающий внутрь `destination`, считается допустимым сценарием, который строковые и буферные операции обязаны обрабатывать корректно. Расхождения с этим правилом считаются дефектом, а не альтернативной нормой API
- **`m_string_length(...)` отвечает мгновенно даже при частых вызовах.** В строковом режиме функция просто возвращает уже посчитанную длину из `->string_length` — никакого повторного сканирования буфера не происходит, поэтому её можно безопасно вызывать в циклах. Работа по поддержанию этой длины в актуальном состоянии происходит один раз внутри тех функций, которые меняют содержимое строки, чтобы не повторять её при каждом запросе. В data-режиме длина не кешируется, и функция честно ищет первый нулевой элемент в пределах `->length`
- **`m_text(...)` и `m_string(...)` никогда не возвращают `NULL`.** В аварийных или некорректных случаях возвращается общий безопасный пустой буфер, заранее заполненный нулями. Его можно читать как пустую строку и безопасно передавать в код, который ожидает строку только для чтения.

## Операции, не зависящие от режима

Эти функции не решают, считать содержимое строкой или обычными данными. Они создают дескрипторы, меняют размер буфера, дают доступ к памяти, освобождают ресурсы или помогают безопасно считать размеры. При этом они не переключают режим дескриптора сами по себе: строковый дескриптор остаётся строковым, data-дескриптор остаётся data-дескриптором.

`m_init(T[, mode])` создаёт значение дескриптора без выделения памяти. Тип `T` задаёт размер одного элемента. Если режим не указан, создаётся data-дескриптор.

`m_init_static(T[, mode])` делает то же самое для глобальных и статических переменных, где начальное значение должно быть записано в фигурных скобках.

`m_create(T, name[, mode])` объявляет локальный дескриптор и сразу инициализирует его. В обычном коде это самый короткий и удобный способ начать работу с `memory`.

`m_resize(desc, element_count[, flags])` задаёт, сколько элементов сейчас логически содержит дескриптор. Если памяти не хватает, библиотека выделяет или расширяет буфер. Если места уже достаточно, может быть изменена только логическая длина. Флаги описаны ниже и позволяют, например, занулять новую область или сразу вернуть лишний резерв системе.

`m_del(desc)` освобождает буфер, который принадлежит дескриптору, сбрасывает длины и оставляет сам дескриптор пригодным для повторного использования. Тип элемента и string/data-режим сохраняются. Если поля дескриптора уже выглядят противоречиво, функция возвращает `FAILURE` и не пытается молча угадывать, как их исправить.

`m_data(T, desc)` возвращает указатель для записи, приведённый к типу `T *`. Перед этим библиотека проверяет, что дескриптор выглядит корректно и что размер элемента в дескрипторе совпадает с `sizeof(T)`. Если указатель безопасно выдать нельзя, возвращается `NULL`.

`m_data_ro(T, desc)` возвращает такой же типизированный указатель, но только для чтения: `const T *`. Это вариант для кода, который должен читать содержимое дескриптора и не должен его менять.

`m_item(T, desc, index)` возвращает указатель на один элемент массива внутри дескриптора. Индекс считается от нуля. Если индекс выходит за текущую логическую длину или тип `T` не совпадает с размером элемента дескриптора, возвращается `NULL`.

`m_item_ro(T, desc, index)` делает то же самое, но возвращает указатель только для чтения.

`m_raw_data(desc)` возвращает записываемый указатель без проверки типа элемента. Минимальная проверка состояния дескриптора всё равно выполняется, но библиотека уже не сравнивает содержимое с `sizeof(T)`, потому что тип `T` здесь вообще не передаётся. При успехе возвращается живой указатель на `desc->data`, а не копия и не отдельное представление. Этот вариант уместен только в низкоуровневом коде, где тип и состояние дескриптора уже известны вызывающей стороне.

`m_raw_data_ro(desc)` возвращает такой же указатель без проверки типа элемента, но только для чтения. Для одного и того же дескриптора `m_raw_data(desc)` и `m_raw_data_ro(desc)` указывают на один и тот же буфер. Такие указатели остаются действительными только до операции, которая может заменить или освободить память дескриптора: `m_resize`, `m_del`, копирование или конкатенация с этим дескриптором в роли назначения.

`m_guarded_byte_size(desc, element_count, &bytes)` переводит количество элементов в байты с проверкой переполнения. Это полезно перед выделением памяти или расчётом смещений: если `element_count * размер одного элемента` не помещается в `size_t`, функция вернёт ошибку.

`m_guarded_add(left, right, &sum)` складывает два значения `size_t` и возвращает ошибку, если результат не помещается в `size_t`.

`m_guarded_subtract(left, right, &diff)` вычитает `right` из `left` и возвращает ошибку, если результат был бы отрицательным для `size_t`, например когда `right > left`.

`m_reset(&ptr)` освобождает обычный указатель через `free(...)` и сразу записывает в него `NULL`. Это удобно для памяти, которая не принадлежит `memory`-дескриптору.

### Флаги поведения `m_resize`

#### Повторное использование уже выделенной памяти

`m_resize(...)` меняет логический размер дескриптора, но не всегда сразу отдаёт лишнюю память системе. Если буфер уменьшился, библиотека обычно оставляет выделенную память как запас на будущее. Когда тот же дескриптор снова вырастет и места в этом запасе хватит, новый вызов аллокатора не потребуется.

Такое поведение полезно для рабочих буферов, которые часто растут и уменьшаются: меньше обращений к аллокатору, меньше лишней работы и меньше фрагментации памяти. `m_resize(desc,0)` очищает логическое содержимое дескриптора и сбрасывает длины, но без `RELEASE_UNUSED` сохраняет уже выделенное хранилище для повторного использования. Если запас больше не нужен и память нужно вернуть системе сразу, используется флаг `RELEASE_UNUSED`: `m_resize(desc,0,RELEASE_UNUSED)` очищает логическое содержимое и физически освобождает хранилище. Этот путь близок к `m_del(desc)` по освобождению памяти, но остаётся resize-операцией: он выражает намерение «обнулить логический размер и вернуть резерв». В обоих случаях string-дескриптор остаётся string-дескриптором, а data-дескриптор остаётся data-дескриптором. Если нужно явно завершить работу с текущим буфером независимо от текущей логической длины, используйте `m_del(desc)`: он освобождает принадлежащее дескриптору хранилище, сбрасывает длины и оставляет тип элемента и string/data-режим пригодными для повторного использования.

#### Флаги

Флаги `m_resize(...)` задают дополнительные действия при изменении размера:

- `ZERO_NEW_MEMORY` зануляет новую часть буфера после роста. Это удобно, когда код ожидает, что только что добавленные элементы уже очищены.
- `RELEASE_UNUSED` сразу возвращает системе лишнюю память после уменьшения буфера.

Флаги можно комбинировать через оператор `|`, например `ZERO_NEW_MEMORY | RELEASE_UNUSED`. Подробности о поведении `m_resize(...)` в строковом и data-режиме описаны в разделах [«Контракт строкового дескриптора»](#контракт-строкового-дескриптора) и [«Работа с данными (бинарный режим)»](#работа-с-данными-бинарный-режим). Когда нужно явно закончить работу с текущим буфером независимо от текущей логической длины, применяется `m_del(desc)`.

`m_resize(...)` возвращает `FAILURE`, если сам дескриптор уже содержит противоречивые поля. Например, если по метаданным в дескрипторе должно лежать больше данных, чем реально покрывает выделенная память (`->actually_allocated_bytes < ->length * ->single_element_size`), или если дескриптор сообщает о выделенной памяти, но `->data == NULL`. В таких случаях библиотека считает дескриптор повреждённым и не подтверждает операцию как успешную, даже если новый размер совпадает со старым.

#### Пример 21. Флаги поведения `m_resize`

Проверяется тестом [`test_libmem_0000_21`](tests/src/test_libmem_0000.c#L874)

В большинстве примеров этого README используется проверка через `TRIUMPH`. Ниже показан более узкий стиль проверки через `CRITICAL`: он реагирует только на жёсткие ошибки.

Чтобы `RELEASE_UNUSED` действительно вернул лишний резерв, пример сначала увеличивает массив за границу одного блока памяти. При последующем уменьшении до четырёх элементов дополнительный блок уже можно освободить.

```c
const size_t points_per_block = MEMORY_BLOCK_BYTES / sizeof(point);
const size_t large_length = points_per_block + 1U;

/* Увеличиваем массив за границу блока и зануляем новые элементы */
if(CRITICAL & m_resize(points,large_length,ZERO_NEW_MEMORY))
{
	return(FAILURE);
}

/* Позже уменьшаем буфер и возвращаем дополнительный блок */
if(CRITICAL & m_resize(points,4,RELEASE_UNUSED))
{
	return(FAILURE);
}
```

`MEMORY_STORAGE_EMPTY` означает пустое состояние без выделенного физического блока. `data` равен `NULL`, а `actually_allocated_bytes` равен `0`.

`MEMORY_STORAGE_HEAP` означает обычный heap-блок, полученный через heap backend.

`MEMORY_STORAGE_ALIGNED_HEAP` означает heap-блок с адресным выравниванием, полученный через aligned backend.

`MEMORY_STORAGE_MMAP_HUGETLB` означает mmap-backed блок, выделенный через явные HugeTLB-страницы.

`MEMORY_STORAGE_MMAP_TRANSPARENT_HUGE_PAGES` означает mmap-backed блок, для которого библиотека запросила Transparent Huge Pages через подсказку ядру. Это значение фиксирует выбранный backend, но не обещает, что ядро действительно разместило все страницы как Huge Pages.
