# Эквивалентность тестов через CLI и конфигурацию

## Цель и область проверки

В плане зафиксированы результаты проверки сценариев приложения в `tests/src/` и необходимые доработки для повторения одинаковых операций через аргументы CLI и конфигурационные файлы. Отсутствие таких повторов означает пробелы в покрытии, но само по себе не доказывает ошибку в работе приложения

Проверка охватывает операции, вывод и сохранённые результаты. Прямые тесты функций и проверки специфического синтаксиса CLI рассматриваются отдельно. Наличие теста конфигурации в другом месте не подтверждает эквивалентность той же операции при одинаковых исходных данных, окружении и ожидаемом выводе

Последовательность проверки форматов вывода соответствует [OUTPUT_MODES_PLAN.md](OUTPUT_MODES_PLAN.md#7-последовательность-реализации-и-проверки). По мере доработки сценариев результаты проверки должны пересматриваться и обновляться

## Проблема и целевая последовательность

Тест только через CLI не подтверждает, что конфигурационный файл задаёт то же поведение. Повтор операции с БД, уже изменённой первым запуском, может проверять другое событие: вместо обновления получится обход без изменений. Разные эталоны для эквивалентных успешных запусков также могут скрыть различия между двумя источниками настроек

Для каждой применимой операции используется следующая последовательность с восстановлением подготовленного исходного состояния перед каждым запуском

| Этап | Источник настроек | Формат вывода | Ожидаемый вывод |
|---|---|---|---|
| 1 | Аргументы CLI | `full` по умолчанию | Полный эталон `<test>_<subtest>_1.txt` |
| 2 | Конфигурация с теми же параметрами | `full` по умолчанию | Тот же эталон, что на этапе 1 |
| 3 | Аргументы CLI этапа 1 с добавлением только `--output=compact` | `compact` | Полный эталон `<test>_<subtest>_2.txt` |
| 4 | Аргументы CLI этапа 1 с добавлением только `--output=machine` | `machine` | Полный эталон `<test>_<subtest>_3.txt` |
| 5, если golden содержит `updated` или `rehashed` | Аргументы CLI этапа 4 с добавлением `--verbose` | `machine` с подробностями | Отдельный полный эталон `<test>_<subtest>_4.txt` |

Дополнительный этап 5 обязателен для сценариев с `updated` или `rehashed`: он проверяет `changed:` внутри скобок и прежние и новые значения изменившихся полей. Если отличий метаданных нет, проверяется отсутствие `changed:`

На всех этапах проверяются код завершения и оба потока вывода, затем повторяются существующие проверки результата операции в БД и файловой системе. На одну операцию нужен один конфигурационный файл для этапа 2; отдельные тесты разбора параметров сохраняют своё назначение

## Предварительная проверка нумерации шаблонов

Проверка и исправление нумерации завершены: [результаты и таблица переименований](TEST_TEMPLATE_NUMBERING_AUDIT.md). Проверены 533 ресурса; переименованы 108 файлов активных тестов и один шаблон отключённого теста 21, пронумерованы функции отключённого теста 14. Общие 37 шаблонов и 4 конфигурации сохранены. Отключённые тесты не включались; `make tests-debug` прошёл успешно — 657 тестов, включая медленные сценарии

1. Собрать перечень golden-шаблонов из `tests/templates/` и каталогов `tests/templates/` встроенных библиотек. Для каждого шаблона определить фактическую тестовую функцию, операцию, поток и формат вывода, проследив ссылки через массивы сценариев и общие вспомогательные функции. Созданные при сборке копии в перечень не включать
2. Для функций приложения вида `testNNNN_S` проверить префикс принадлежности `NNNN_SSS`: четыре цифры номера группы тестов и три цифры номера подтеста. Выявить неверные префиксы, ссылки на отсутствующие файлы, неиспользуемые файлы и пересечения целевых имён. Также проверить соответствие имён конфигурационных файлов использующим их подтестам. Для общих ресурсов несовпадение номера с одним или несколькими потребителями само по себе не является ошибкой
3. Для набора stdout одной операции использовать суффикс `1` для full, `2` для compact, `3` для machine и `4` для дополнительного machine с `--verbose`. CLI и конфигурационный запуск в full используют общий эталон с суффиксом `1`; конфигурационный файл имеет то же имя с расширением `.conf`. Для CLI-запусков compact и machine отдельные конфигурации не нужны. Для дополнительных операций или потоков назначение числовых суффиксов должно быть явно определено, поэтому нельзя считать существующий суффикс обозначением формата без проверки его использования
4. Зафиксировать общие шаблоны и все места их использования. При одинаковом ожидаемом выводе разные тесты могут использовать один полный шаблон; создавать копии ради совпадения номеров не требуется. Тесты без нумерованных подтестов и схемы именования встроенных библиотек проверять по фактическим функциям; не считать часть имени файла доказательством существования отдельного подтеста
5. До переименования подготовить соответствие старое имя → новое имя. Сначала перенести шаблоны, занимающие номера чужих подтестов, в правильные группы, использовать `git mv`, обновить все ссылки в коде и планах, сохранить содержимое шаблонов, кроме ожидаемых путей конфигурации, если они меняются при её переименовании. После каждой группы переименований проверить ссылки и выполнить `make tests-debug`

Примеры требуемого соответствия:

| Тестовая функция | full | compact | machine |
|---|---|---|---|
| `test0016_2` | `0016_002_1.txt` | `0016_002_2.txt` | `0016_002_3.txt` |
| `test0016_3` | `0016_003_1.txt` | Не реализовано | Не реализовано |
| `test0016_4` | `0016_004_1.txt` | `0016_004_2.txt` | `0016_004_3.txt` |

Например, если файл `0016_002_2.txt` используется только в `test0016_3`, подходящим именем будет `0016_003_1.txt`: `002` указывает на другой подтест. Имя `0016_003.txt` для отдельного compact-эталона `test0016_2` также не отражает номер подтеста и вариант. Это правило не требует разделять общий шаблон, которым несколько тестов проверяют одинаковый вывод

## Особые случаи

- `test0013_1` и `test0038_1–_5` проверяют состояние БД без полных эталонов вывода. Проверки отсутствия БД, сохранения контрольных точек и возобновления должны сохраниться. Перед добавлением проверки вывода определить значимые потоки с воспроизводимым содержимым; выбранные операции повторять через конфигурацию при тех же условиях сохранения контрольных точек и прерывания
- В `test0013_3`, `test0018_5`, `test0028_7` и `test0040_8` есть CLI- и конфигурационные варианты с различающейся диагностикой, включая номера строк конфигурации. Для намеренных различий сохранять полные отдельные эталоны по источникам настроек. Общий шаблон не должен скрывать такую диагностику или ослаблять проверку ожидаемого вывода
- Прямым тестам функций не нужна искусственная пара CLI/конфигурация. Проверки написания коротких опций, отсутствующих аргументов CLI, справки и порядка параметров также сохраняют собственное назначение. Например, `test0040_3` проверяет короткие опции цвета; эквивалентность длинных опций и конфигурации отдельно проверяется в `test0040_2`
- Сравнение без записи, операция без изменений или dry-run могут повторно использовать исходные данные, если они остаются неизменными. Само отсутствие копирования не является дефектом. Необходимо подтвердить сохранность значимого состояния, а не добавлять избыточное копирование
- Создание, обновление, удаление, миграции и прерываемое хеширование требуют явной подготовки и восстановления исходного состояния. Тесты обновления версии должны защищать каждую БД, которая может быть обновлена, включая эталонные БД при будущем повышении версии

## Правила реализации

1. Дополнять существующие сценарии операций с помощью `argument_test_case` и `run_and_match_templates()`. Подготовку фикстур и проверки результата оставлять внутри сценария; использовать существующие общие вспомогательные функции вместо введения отдельной тестовой инфраструктуры
2. Сохранять состояние непосредственно перед сравниваемой операцией. Для обновления изменённого файла оставлять сам изменённый файл на месте и перед каждым запуском восстанавливать БД до обновления. Восстанавливать файлы только тогда, когда сценарий их меняет; повторное создание может изменить временные метки и нарушить условия проверяемого события
3. Одинаково восстанавливать значимые значения окружения, состояние моков, права доступа и условия прерывания или сохранения контрольных точек. Сохранять одинаковое значение `TESTING` внутри каждой пары CLI/конфигурация
4. Хранить полные конфигурационные файлы и golden-шаблоны с числовыми именами в `tests/templates/`. Использовать ресурсы, уже скопированные в `prepare()`; отдельные копии нужны только для изменения содержимого, подстановки значений или проверки обязательного имени конфигурации по умолчанию
5. Сопоставлять каждый непустой поток целиком с самостоятельным шаблоном. Пустые потоки проверять явно, а не через `NULL`. Ограничивать переменные поля и сохранять ожидаемые окончания строк; не собирать эталоны из фрагментов и не удалять вывод ради успешного сравнения
6. Использовать универсальный ANSI-шаблон `(?:\x1B\[[0-9;]*m)*` там, где оформление может присутствовать. Эталон машинного вывода по умолчанию должен отвергать ANSI-последовательности. Допуск необязательного ANSI-оформления сам по себе не доказывает наличие цвета в compact
7. После каждого этапа повторять проверки смысла результата: ожидаемых записей и путей, завершённых хешей, временных меток, защищённых записей, отсутствия БД или неизменности данных — в зависимости от операции. Одного совпадения вывода недостаточно
8. Сохранять состояние, необходимое следующим тестам, и выполнять очистку даже после неудачной проверки. Добавлять короткие комментарии, объясняющие восстановление исходного состояния и каждый логический этап

## Предлагаемый порядок доработки и критерии завершения

1. Проверка и исправление нумерации завершены, включая отключённые тесты; общие ресурсы сохранены. При добавлении этапов поддерживать установленное соответствие имён
2. Сначала дополнить простые пары с одной операцией, например `test0016_3` и сценарии фильтрации файлов, затем добавить этапы compact/machine
3. Дополнить частично повторяемые сценарии, используя существующие полные эталоны и добавляя недостающие сочетания настроек
4. Дополнить последовательности связанных операций и миграции, затем сценарии ошибок доступа, прерывания и сохранения контрольных точек с необходимым восстановлением состояния
5. После каждого небольшого изменения просмотреть diff и выполнить `make tests-debug`, включая медленные сценарии. При сбое сборки или теста прекратить дальнейшие изменения и обсудить причину и предлагаемое исправление согласно `AGENTS.md`
6. Удалять находки из списка или отмечать их устранёнными только после успешной проверки всех применимых этапов и результатов операций. Фиксировать намеренные исключения и обновлять этот план по мере реализации
