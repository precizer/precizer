# Концептуальный план режимов вывода full, compact и machine

Статус: реализация, документация и автоматические проверки завершены; требования повторной ручной проверки отмеченных функций сохраняются

В precizer должны быть доступны существующий вывод для человека и машинный режим, который скрипты смогут разбирать без распознавания заголовков и анализа соседних сообщений. Машинный режим должен охватывать создание, обновление и сравнение баз данных

В [обсуждении №172](https://github.com/precizer/precizer/issues/172) предложен альтернативный вывод сравнения в стиле diff. В этом плане для обозначения событий используются слова, чтобы формат мог также описывать обновление метаданных, проблемы доступа и другие события, связанные с файлами

## 0 Режимы вывода и конфигурация

- Поддержать `--output=full|compact|machine` и короткий вариант `-O full|compact|machine`; режим по умолчанию — `full`
- `compact` и `machine` выводят одинаковые записи. Без явно заданного `color` для `full` и `compact` применяется `auto`, для `machine` — `never`. Явное значение `color` из CLI или конфигурации имеет приоритет: `always` включает цвет даже в `machine`, `auto` включает штатное автоопределение, `never` отключает цвет
- Все описанные далее правила формата и поведения `machine` распространяются на `compact`, кроме значения цвета по умолчанию. Оба используют существующий флаг логгера `MACHINE`; отдельный флаг `COMPACT` не нужен
- Имена CLI-опций и ключи конфигурации чувствительны к регистру. Только именованные значения распознаются без учёта регистра; пути, имена файлов и регулярные выражения сохраняются буквально
- Добавить параметр `output` в конфигурацию и учесть его при инициализации и очистке конфигурации
- Определить в заголовочном файле проекта `OUTPUT_FULL`, `OUTPUT_COMPACT` и `OUTPUT_MACHINE`
- В режиме `full` использовать `dropped as missing PATH` при удалении записи отсутствующего файла, а при сравнении добавлять перед путями `added`, `deleted` и `mismatch` с цветами из раздела 3. Заголовки сравнения уточняются по разделу 3; остальные сообщения сохраняются, кроме итоговой диагностики `WARNING` (раздел 2)
- Режим `machine` должен представлять существующие результаты, не меняя обработку файлов и правила определения изменений в базе данных

## 1 Форматы записей machine

При создании и обновлении базы данных каждая запись должна содержать три поля:

```text
keyword [details] PATH
```

Одна физическая строка описывает одно событие, относящееся к одному файлу или директории. При создании и обновлении базы данных квадратные скобки обязательны. При сравнении баз данных используются только ключевое слово и путь: `keyword PATH`, без пояснения в скобках. Каждая строка содержит достаточно информации для определения события без предшествующего заголовка

Относительный путь передаётся обычному логгеру без дополнительного экранирования, добавления кавычек или сокращения. Сохраняется штатная обработка управляющих символов и цветовой разметки, поэтому побайтовое сохранение произвольного пути не гарантируется, в том числе для последовательностей вроде `@{red}`:

- При создании и обновлении базы данных всё после закрывающей скобки пояснения и одного разделяющего пробела до конца строки является относительным путём
- При сравнении баз данных разделителем служит первый пробел после ключевого слова. Всё после этого пробела до конца строки является относительным путём

Пробелы, кавычки, обратные косые черты и квадратные скобки внутри пути сохраняются и считаются частью пути. Для всех режимов принято условие: пути не содержат символов перевода строки

Сообщения, передаваемые для вывода в режимах `full`, `compact` и `machine`, не должны содержать внутренних переводов строки. Завершающий перевод строки служит разделителем сообщений. Если при реализации обнаруживается сообщение с внутренним переводом строки, дальнейшие изменения останавливаются до обсуждения способа его обработки

Ключевые слова действий используются в завершённой форме, например: `added`, `dropped`, `deleted`, `rehashed`, `updated`. Ключевые слова `inaccessible`, `error`, `critical` и `mismatch` описывают состояния или результаты

Ключевые слова должны оставаться стабильными и не зависеть от языка интерфейса. В квадратных скобках помещаются вариативные пояснения: подробности изменений, прежние и новые значения, описания ошибок. Парсинг в скриптах может быть настроен так, чтобы целиком пропускать поле `[details]` и обрабатывать только ключевое слово и путь. Такой разбор не зависит от формулировок пояснений, в том числе сообщений операционной системы

Специальное экранирование `[details]` не предусматривается. Пояснения формируются из фиксированных описаний событий, числовых значений, единиц измерения, дат и сообщений `strerror()`. Пути и пользовательские шаблоны в пояснения не включаются. В фиксированных описаниях и форматах числовых значений нет закрывающих квадратных скобок, переводов строк или других управляющих символов

В текущем коде включение пользовательской локали отключено. При проверке `strerror()` для 135 кодов ошибок в локали `C` в текущем окружении таких символов также не обнаружено. Для согласованного состава пояснений разбор выполняется по первой закрывающей скобке, после которой пропускается один разделяющий пробел. Цветовые управляющие последовательности исключаются параметром `--color=never`

Одна строка описывает одно событие, а не обязательно весь результат обработки файла. Один путь может встречаться в нескольких записях, если с ним связаны разные события. Например, хеширование файла было возобновлено с сохранённой позиции, а затем снова прервано. Сообщения о возобновлении и прерывании относятся к одному пути, но описывают два разных события

В обычном режиме `full` необходимо сохранить итоговый вывод запомненных сообщений (`REMEMBER`) по существующим правилам. В техническом режиме `machine`, предназначенном для скриптов, сохранение новых сообщений в историю и её итоговый вывод не выполняются. Ранее сохранённая история не очищается. Сами события выводятся в компактном формате по мере возникновения, но не повторяются при завершении программы, чтобы автоматическая обработка не учитывала одно событие несколько раз

## 2 Записи при создании и обновлении базы данных

В таблицах сопоставлены сообщения режима `full` и согласованные записи режима `machine`. Полный вариант показан без диагностических префиксов и дополнительных уточнений об изменении метаданных. Цвет относится только к ключевому слову в режиме `machine`; перед разделяющим пробелом цвет сбрасывается, пояснение и путь выводятся обычным цветом

Основные события:

| Полный вариант (`full`, существует) | Технический вариант (`machine`) | Цвет |
| --- | --- | --- |
| `added PATH` | `added [as new] PATH` | Зелёный |
| `rehashed PATH` | `rehashed [file] PATH` | Тёмно-жёлтый |
| `updated metadata PATH` | `updated [metadata] PATH` | Синий |
| `inaccessible file PATH` | `inaccessible [file] PATH` | Оранжевый |
| `inaccessible directory PATH` | `inaccessible [directory] PATH` | Оранжевый |
| `error "MESSAGE" when reading PATH` | `error [read error: MESSAGE] PATH` | Красный |

При сочетании `--output=machine --verbose` существующие уточнения об изменениях метаданных (`changed: … was:… now:…`) помещаются внутрь квадратных скобок после основного пояснения. В записи `rehashed` при наличии этих уточнений слово `file` опускается. Перечисляются те же изменения и прежние и новые значения, которые сейчас показывает `--verbose`, например:

```text
rehashed [changed: lsize was:1KiB, now:2KiB] path/file.txt
```

Без `--verbose` сохраняется краткое пояснение. С `--verbose` запись остаётся одной строкой, путь располагается после закрывающей скобки. Этот параметр не включает дополнительный служебный вывод

При обходе `added` и `dropped` описывают изменения записей о файлах в базе данных. Запись `dropped` не означает, что precizer удалил исходный файл

Дополнительные форматы соответствуют существующим сообщениям и сохраняют условия и приоритет их вывода

Добавление и обновление записей:

| Полный вариант (`full`, существует) | Технический вариант (`machine`) | Цвет |
| --- | --- | --- |
| `added as included PATH` | `added [as included] PATH` | Зелёный |
| `added as empty PATH` | `added [as empty] PATH` | Зелёный |
| `updated as included PATH` | `updated [as included] PATH` | Синий |
| `updated as empty PATH` | `updated [as empty] PATH` | Синий |

`as included` обозначает файл, выбранный правилом включения, а `as empty` — пустой файл. Действие относится к добавлению или обновлению записи в базе данных

Результаты применения правил включения и игнорирования:

| Полный вариант (`full`, существует) | Технический вариант (`machine`) | Цвет |
| --- | --- | --- |
| `ignored & not added PATH` | `ignored [not added] PATH` | Серый |
| `ignored & not updated PATH` | `ignored [not updated] PATH` | Серый |
| `ignored directory PATH` | `ignored [directory] PATH` | Серый |
| `included directory PATH` | `included [directory] PATH` | Зелёный |

Игнорируемый файл не добавляется в базу данных либо его существующая запись не обновляется. Для директорий сообщается результат применения правил. `included [directory]` не означает добавление записи о директории в базу данных

Удаление и сохранение записей при проверке отсутствующих файлов:

| Полный вариант (`full`, существует) | Технический вариант (`machine`) | Цвет |
| --- | --- | --- |
| `dropped as missing PATH` | `dropped [as missing] PATH` | Синий |
| `dropped as ignored PATH` | `dropped [as ignored] PATH` | Синий |
| `dropped as inaccessible PATH` | `dropped [as inaccessible] PATH` | Синий |
| `kept inaccessible PATH` | `kept [inaccessible] PATH` | Оранжевый |

`as missing` означает, что файл больше не найден. Удаление игнорируемых записей требует `--db-drop-ignored`, недоступных — `--db-drop-inaccessible`. Без запроса удаления недоступная запись сохраняется, что обозначается словом `kept`

Недоступность при этой проверке включает отказ в доступе и ошибку проверки доступа. Причина удаления определяется существующей логикой: игнорирование проверяется раньше доступности. Для игнорируемой записи, удаляемой по `--db-drop-ignored`, используется `as ignored`, даже если файл отсутствует. Защищённые контрольной суммой записи сохраняются; при недоступности соответствующих файлов выводится сообщение о нарушении защиты. Сохранение обычной игнорируемой записи без `--db-drop-ignored` не создаёт отдельного события

Хеширование:

| Полный вариант (`full`, существует) | Технический вариант (`machine`) | Цвет |
| --- | --- | --- |
| `rehashed from the beginning PATH` | `rehashed [from the beginning] PATH` | Тёмно-жёлтый |
| `rehash resumed from OFFSET PATH` | `resumed [hashing from OFFSET] PATH` | Тёмно-жёлтый |
| `hashing gracefully interrupted at OFFSET PATH` | `interrupted [hashing at OFFSET] PATH` | Оранжевый |

`from the beginning` означает завершённый расчёт заново с начала файла, поскольку сохранённое частичное состояние больше не подходит. `resumed` сообщает о продолжении расчёта в этом сеансе с сохранённой позиции, но само по себе не утверждает, что расчёт завершён. `interrupted` обозначает корректное прерывание на указанной позиции

`OFFSET` сохраняет существующее представление объёма данных, например `128MiB`. После возобновления и повторного прерывания для одного пути допустимы обе строки: `resumed` и `interrupted`. Добавление записи о новом файле также может сопровождаться прерыванием: `added` сообщает о записи в базе данных, а не о завершении хеширования

Защита контрольной суммы:

| Полный вариант (`full`, существует) | Технический вариант (`machine`) | Цвет |
| --- | --- | --- |
| `locked checksum PATH` | `locked [checksum] PATH` | Зелёный |
| `rehashed & locked checksum matched PATH` | `rehashed [locked checksum matched] PATH` | Тёмно-жёлтый |
| `checksum locked & mismatch, data corrupted PATH` | `critical [locked checksum mismatch, data corrupted] PATH` | Красный |
| `checksum locked, data corruption detected PATH` | `critical [locked checksum, data corruption detected] PATH` | Красный |
| `checksum locked, file disappeared PATH` | `error [locked checksum, file disappeared] PATH` | Красный |
| `checksum locked, access denied PATH` | `error [locked checksum, access denied] PATH` | Красный |
| `checksum locked, access check failed PATH` | `error [locked checksum, access check failed] PATH` | Красный |

`locked` сообщает о создании записи для файла с защищаемой контрольной суммой. Само событие не подтверждает завершение расчёта: при прерывании отдельно выводится `interrupted`. `locked checksum matched` означает, что повторный расчёт завершён и контрольная сумма совпала с защищённой

`critical` обозначает два события нарушения целостности: несовпадение защищённого хеша и недопустимое изменение метаданных. Цвет остаётся красным; правила продолжения работы и код завершения сохраняются. Ошибки чтения, исчезновение и недоступность файла сохраняют `error`

При завершении с `WARNING` без `FAILURE` итоговое сообщение — `The precizer completed with warnings`, с флагом `EVERY`: оно выводится в `full` без `--silent` и не появляется в `compact`/`machine`. При наличии `FAILURE` сохраняется прежнее сообщение `ERROR`. Код завершения не меняется

`locked checksum mismatch` сообщает о несовпадении повторно вычисленной и защищённой контрольных сумм. `data corruption detected` без `mismatch` означает, что существующие правила защиты обнаружили недопустимое изменение метаданных; эта строка не утверждает, что выполнен пересчёт и обнаружено несовпадение хешей. Остальные причины различают исчезновение защищённого файла, отказ в доступе и ошибку проверки доступности

Ошибки получения сведений о пути и обхода:

| Полный вариант (`full`, существует) | Технический вариант (`machine`) | Цвет |
| --- | --- | --- |
| `cannot stat "MESSAGE" when reading PATH` | `error [stat error: MESSAGE] PATH` | Красный |
| `fts error "MESSAGE" when reading PATH` | `error [fts error: MESSAGE] PATH` | Красный |

`stat error` означает невозможность получить метаданные пути, `fts error` — ошибку обхода файловой системы для этого пути

`MESSAGE` — существующий текст `strerror()`. Эти события, как и `error [read error: MESSAGE] PATH`, относятся к конкретному относительному пути и используют машинный формат. Ошибка чтения включает существующие случаи неудачного открытия файла для чтения. Ключевое слово `error` не меняет правила продолжения работы или код завершения программы

Источники событий: [show_file.c](src/show_file.c), [directory_show.c](src/directory_show.c), [directory_access.c](src/directory_access.c), [file_list.c](src/file_list.c), [db_delete_missing_metadata.c](src/db_delete_missing_metadata.c) и [show_locked_checksum.c](src/show_locked_checksum.c). Символические ссылки сейчас учитываются в счётчике без отдельных строк о каждом пути; новые события для них не добавляются. Обычные директории также не получают отдельной строки только по факту посещения

При обычном запуске запись о завершённом действии должна описывать действительно завершённое действие. Для прерванного расчёта нужно соответствующее событие, без утверждения об успешном завершении хеширования или проверки контрольной суммы. Для `--dry-run` сохраняется существующее поведение по правилу раздела 4

## 3 Записи при сравнении

Во всех режимах строки результатов сравнения содержат ключевое слово и путь, без квадратных скобок. В `full` без `--silent` сохраняются заголовки категорий и служебные сообщения; в `compact`, `machine` и при `--silent` они не выводятся:

```text
added path/new.txt
deleted path/deleted.txt
mismatch path/file.txt
```

Направление сравнения — от первой базы данных ко второй:

- `added PATH` — путь присутствует только во второй базе данных. Цвет — зелёный
- `deleted PATH` — путь присутствует только в первой базе данных. Цвет — синий
- `mismatch PATH` — путь присутствует в обеих базах данных, а сохранённые контрольные суммы различаются. Цвет — оранжевый

Заголовки `full`: `deleted` — `These files are no longer in SECOND_DB but are still present in FIRST_DB`; `added` — `These files are present in SECOND_DB but absent from FIRST_DB`. В обоих случаях сначала указывается вторая база, затем первая

Эти записи описывают различия между двумя сохранёнными состояниями. Они не устанавливают, когда файл был создан или удалён, а само сравнение не выполняет обозначенные добавления или удаления

Эта палитра одинакова для `full`, `compact` и `machine` при включённом цвете, применяется только при `--compare` и определяется отдельно от палитры обхода. Окрашивается только ключевое слово (`added`, `deleted` или `mismatch`). Сразу после него цвет сбрасывается; пробел и `PATH` выводятся стандартным цветом терминала

## 4 Машинные записи и технические ошибки

Добавить в логгер самостоятельный флаг `MACHINE` для сообщений, предназначенных для скриптов:

- `MACHINE` занимает отдельный бит. Существующая маска `EVERY` остаётся без изменений и не включает `MACHINE`
- При `--output=machine` включается режим логгера `MACHINE`. Логгер допускает только сообщения с флагом `MACHINE` или `ERROR`, с сохранением приоритета `SILENT`
- Обычный `slog(ERROR, …)` выводится при активном режиме `MACHINE`. Существующие вызовы, тексты и флаги технических ошибок сохраняются; отдельные варианты для `machine` не добавляются
- Флаги `EVERY`, `REGULAR`, `VERBOSE` и `TRACE` не дают видимости в режиме `MACHINE`, если сообщение не содержит ни `MACHINE`, ни `ERROR`
- Машинные записи выводятся через `MACHINE | UNDECOR`, без диагностических префиксов. Записи сравнения дополнительно получают `VISIBLE_IN_SILENT`
- Для сообщений `ERROR` сохраняется обычный префикс `ERROR: `, если вызов не содержит `UNDECOR`
- При `--output=full` записи, помеченные только режимом `MACHINE`, не показываются
- В режиме `machine` параметр `--verbose` управляет подробностями внутри скобок через `config->verbose`, не включая обычный режим логгера `VERBOSE`
- Общие вызовы могут содержать `REMEMBER`: в `machine` функция `rational_remember()` сразу возвращается без обращения к таблице истории. Сохранение новых сообщений и итоговый повтор выполняются только в `full`; ранее сохранённая история не очищается
- Режим логгера выбирает одна общая функция по приоритету `SILENT` → `MACHINE` → `VERBOSE` → `TESTING` → `REGULAR`. Условия соответственно: `silent = true`, `output = compact` или `output = machine`, `verbose = true`, `TESTING=true` в тестовой сборке, обычный режим по умолчанию. `output = full` не перекрывает `VERBOSE` или `TESTING`
- Приоритеты не зависят от порядка разных параметров. Повторное указание одного параметра заменяет его значение. Запрошенные `silent`, `verbose` и `output` хранятся отдельно от режима логгера; настройки с меньшим приоритетом не стираются. После отключения старшего режима общая функция выбирает следующий активный. Для `SILENT` сохраняются существующие правила подавления сообщений

В каждом месте, где событие имеет два представления, текст и флаги выбираются локальным `if(config->output != OUTPUT_FULL) ... else ...`, где первая ветвь обслуживает `compact` и `machine`. Условия возникновения события остаются общими для обеих ветвей. Логгер определяет видимость выбранного сообщения по его флагам. Одинаковые сообщения и общие фрагменты с одинаковыми правилами вывода объединяются в один вызов с `EVERY | MACHINE`; остальные флаги сохраняются. Так выводятся строки результатов сравнения и общие завершающие пути в `show_file()`

Служебные сообщения о запуске, конфигурации, обслуживании БД и завершении, заголовки обхода, прогресс и статистика не помечаются `MACHINE` и скрываются логгером в режиме `machine`

К техническим ошибкам программы относятся в том числе ошибки ОС, связанные с внешними факторами. Если ошибка не перечислена в разделе 2 как машинное событие, она сохраняет существующий диагностический вывод и является исключением из формата машинных записей. Для такой диагностики не требуется придумывать относительный путь или преобразовывать сообщение в `keyword [details] PATH`. Обычный `slog(ERROR, …)` продолжает писать в stdout, поэтому его сообщения могут находиться в одном потоке с машинными записями

Цвет — необязательное оформление, которое не должно нести информацию, необходимую для разбора. Режим вывода определяет только значение цвета по умолчанию согласно разделу 0. Явный `--color` или ключ `color` имеет приоритет над ним независимо от порядка параметров. Запрошенное значение и факт его явного задания хранятся отдельно от применённого значения: переключение `output` пересчитывает только не заданный явно цвет. Штатные правила `auto`, `always`, `never` сохраняются; в примерах для скриптов используется `--color=never`

Существующее поведение `--dry-run`, включая `--dry-run=with-checksums`, сохраняется без изменений. Выбор `full`, `compact` или `machine` меняет только представление выводимых сообщений по правилам этого плана

Пустой поток означает, что записи не выводились. Для определения успешного завершения по-прежнему необходимо проверять код завершения процесса

## 5 Ошибки входных путей и сочетания параметров

- Диагностика входных путей и обязательной БД сохраняет существующие тексты и флаги без специальных машинных ветвей и дублей. Видимость определяется логгером: `ERROR` допускается с учётом `SILENT`, сообщения только с `EVERY` скрыты в `machine`. Наличие пути в каждой ошибке не требуется. Правила продолжения работы и коды завершения сохраняются
- В `machine` параметр `--quiet-ignored` целиком скрывает записи `ignored [not added]`, `ignored [not updated]`, `ignored [directory]`, `included [directory]`, `added [as included]` и `updated [as included]`, включая пояснение и путь. Остальные записи, в том числе `dropped [as ignored]`, ошибки и прерывания, этот параметр не скрывает
- В `machine` параметр `--progress` принимается, но не включает индикатор и предварительный обход для подсчёта. Предупреждение об игнорировании параметра не выводится. Служебный вывод отсекается по флагам согласно разделу 4
- При `--silent` сообщения обхода и обычные `ERROR` подавляются. При сравнении во всех форматах остаются только записи `added PATH`, `deleted PATH` и `mismatch PATH`, без заголовков независимо от числа выбранных категорий
- `--compare-filter`, `--ignore` и `--include` сохраняют своё назначение. Параметры управления выводом не должны оставлять неполные записи

## 6 Документация и примеры в README

Описать параметр, режим по умолчанию, форматы записей при обходе и сравнении, уточнения при `--verbose`, значения событий, направление сравнения, цвета, обычную обработку относительных путей логгером и правила отделения пути от остальной записи в `README.ru.md`, затем обновить перевод на американский английский в `README.md`

В обоих README явно пояснить, что квадратные скобки содержат вариативные сообщения. Скрипты могут целиком пропускать поле `[details]` и обрабатывать только ключевое слово и путь, не завися от формулировок пояснений

Также описать исключение для обычных сообщений о технических ошибках: они сохраняются и могут присутствовать в stdout рядом с машинными записями. Учесть такие сообщения в примерах обработки вывода

Добавить примеры обхода и сравнения, а также короткие примеры разбора обоих форматов. Для обхода извлекается ключевое слово, а поле пояснения в скобках можно целиком пропускать либо сохранять при необходимости. Путь занимает весь остаток строки после закрывающей скобки пояснения и одного разделяющего пробела. Для сравнения ключевое слово отделяется первым пробелом, а весь остаток строки является путём. Путь не разбивается по пробелам, его содержимое не обрезается и не преобразуется. Примеры должны показывать разбор с пропуском пояснения, обрабатывать путь с пробелами, использовать вывод без цвета и проверять код завершения процесса

Примеры команд для планируемого интерфейса:

```sh
./precizer --output=machine --color=never --database=files.db /data
./precizer --output=machine --color=never --compare before.db after.db
```

Примеры в README должны пояснять, что это компактный формат событий со словесными обозначениями, а не патч для применения средствами работы с diff

## 7 Последовательность реализации и проверки

По мере внесения изменений план пересматривается. Отклонения от плана по инициативе разработчика требуют утверждения автора; соответствующие положения плана корректируются по ходу работ согласно утверждённому изменению

Обычно каждый пункт выполняется отдельным небольшим шагом с тестами и полными эталонами stdout/stderr по правилам `AGENTS.md`. По решению автора реализация пунктов 9–18 выполнена одним блоком; новые автоматические проверки для них отложены до отдельного этапа перед пунктом 19. По решению автора текущий этап ограничен проверками `--output`; общая доработка эквивалентности CLI и конфигурации отложена. Существующие конфигурационные проверки сохраняются, недостающие повторы ради унификации не добавляются. Каждый сценарий сначала выполняется через CLI с выводом `full` по умолчанию. Следом из того же состояния повторяется исходная CLI-команда с добавлением только `--output=compact` или `--output=machine`, каждый запуск со своим полным эталоном: `<номер теста>_<номер подтеста>_<вариант>.txt`, где варианты `1`, `2`, `3` соответствуют `full`, `compact`, `machine`. После завершённого изменения кода проверяются изменения и выполняется `make tests-debug`, включая медленные сценарии. При сбое сборки или теста дальнейшие изменения останавливаются для обсуждения причины и решения

Если golden-шаблон сценария содержит записи `updated` или `rehashed`, при добавлении запуска `--output=machine` обязательно добавить ещё один CLI-запуск с `--output=machine --verbose` из того же исходного состояния и с отдельным полным golden-шаблоном. Он должен проверять блок `changed:` внутри скобок и прежние и новые значения изменившихся полей; при отсутствии отличий метаданных — отсутствие `changed:`

Для функций с отметкой о ручной проверке отдельное разрешение не требуется. После изменения обязательно явное уведомление разработчика в итоговом ответе с перечнем функций, их расположением, сутью изменений и требованием повторной построчной проверки человеком
